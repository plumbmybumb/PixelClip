# PixelClip protocol — v1

This is the contract between the iOS app, the `core/` library, and the firmware. Change it only by
editing this file first; both sides implement exactly what is here.

## 1. Display

- 536 × 240 pixels, landscape. Origin top-left. The whole panel is visible; layouts may use all of it.
- Pixel format on the wire and in `.hca` files: **RGB565 big-endian** (byte 0 = `RRRRRGGG`, byte 1 = `GGGBBBBB`).
  This is the byte order the RM67162 panel consumes over QSPI, so the device never swaps bytes.
- The phone is responsible for scaling, cropping, dithering and colour conversion. The device only decompresses and blits.

## 2. `.hca` asset format (Hair Clip Animation)

Little-endian integers except pixel data (see above). A still image is a 1-frame animation.

```
Header (32 bytes)
 off size field
  0   4   magic            "HCA1"
  4   2   width            u16   (536 for full-screen; smaller allowed for glyph atlases)
  6   2   height           u16
  8   2   frame_count      u16   >= 1
 10   1   pixel_format     u8    0 = RGB565BE
 11   1   compression      u8    0 = raw, 1 = RLE16 (below)
 12   2   loop_count       u16   0 = loop forever (informational; playlist decides)
 14   2   flags            u16   bit0 = is_glyph_atlas (frames are glyphs, not an animation); bit1 = is_strip (a single wide frame the device scrolls, see §4 `scroll`)
 16   4   frame_table_off  u32   always 32 in v1
 20   4   data_size        u32   total file size in bytes
 24   8   reserved         zero

Frame table (frame_count entries × 12 bytes), at frame_table_off
  0   4   offset           u32   absolute file offset of frame data
  4   4   length           u32   compressed length in bytes
  8   2   duration_ms      u16   display time; 0 means "use playlist/default" (default 100 ms)
 10   2   flags            u16   reserved, zero

Frame data: width*height pixels, row-major, top-to-bottom.
```

### RLE16 (compression = 1)
A stream of runs until `width*height` pixels are produced. Each run starts with a u16 LE control word `c`:
- `c & 0x8000 == 0`: **literal** run. `n = (c & 0x7FFF) + 1` pixels follow (2 bytes each, RGB565BE).
- `c & 0x8000 != 0`: **repeat** run. `n = (c & 0x7FFF) + 1`; one pixel (2 bytes) follows and is repeated `n` times.
Runs may cross row boundaries. Max run length 32768. A decoder MUST reject streams that overrun the frame.

**Exactness (normative, matches `core/`):** an RLE16 frame must consume exactly its frame-table `length` bytes and produce exactly `width*height` pixels; underruns, overruns and trailing bytes are all rejected. `length` is even and lies in `[4*ceil(px/32768), 4*px]`. A raw frame has `length == width*height*2`. Encoders must write exact lengths. Upload handlers require the HTTP body size to equal `data_size`.

Encoder guidance (phone side): emit a repeat run for ≥ 3 identical pixels, literal otherwise; this gives ~1–5 KB per dark frame and never worse than raw + 0.01%.

### Asset ids
`[a-z0-9][a-z0-9-]{0,31}`. Generated by the app (UUID prefix or slug). The app keeps the mapping id → human name; the device stores only ids. Content identity is the SHA-256 of the file.

## 3. WiFi session

- Long-press BOOT (≥ 1.5 s) toggles **upload mode**. On entry the clip shows a splash "WiFi: `<ssid>`" for 3 s, then blanks the display and starts a SoftAP.
- SSID `PixelClip-XXXX` (ASCII, no accent, so hotspot joining is reliable; XXXX = last 2 MAC bytes, hex upper). WPA2-PSK, default passphrase `pixelclip-2026` (changeable via `/config`). Channel 6, max 1 station, TX power capped (≈ 8–11 dBm) to protect the battery.
- IP `192.168.4.1`, DHCP for the phone, mDNS `pixelclip.local`.
- The AP shuts down and the display returns after `upload_timeout_s` (default 120) with no HTTP request, or immediately on `POST /session/end`, or on another long-press.
- The phone joins via `NEHotspotConfiguration` (join-once) and talks plain HTTP. No TLS, no auth beyond WPA2.
- **Display during a session**: by default the screen stays on and keeps playing, with a small accent-coloured connection mark top-right; `/show`, `/next`, `/brightness` and `/screenshot` are live. Config `display_during_upload:false` turns the panel off for the session instead (needed for cells rated ≤ 0.2 A).
- **Findable while linked**: the clip keeps advertising while a central is connected (two links allowed; a
  second central becomes the current one and the previous link is dropped), and a central that sends nothing for
  20 s is disconnected by the clip. A client that holds a link must read or write at least every 20 s, or reconnect
  when it needs the clip. Reason: iOS can keep a link the app has released, and a clip that stopped advertising would then
  look "away" to every scan.
- **Always reachable**: config `wifi_always_on:true` keeps the AP up with no idle timeout (≈ 100 mA idle, roughly halves wear time); `/status.session` reports `always_on`, `display_on` and `clients`. While always-on, `POST /session/end` returns `{"ok":true,"always_on":true}` and leaves the AP up; a long press, BLE `0x02` or the battery floor switch it off for the current boot.
- **BLE wake ("doorbell")**: the clip advertises over Bluetooth LE as `PixelClip-XXXX` with a fixed 128-bit service UUID (see firmware/README.md and `firmware/components/ble/include/pixelclip_ble_uuids.h`). Writing `0x01` to the `wake` characteristic starts upload mode exactly like a long press; `0x02` ends it. A `status` characteristic is readable and notifies: `mv u16 LE, pct u8, flags u8 (bit0 session_active, bit1 usb_present, bit2 clock_ok, bit3 playing, bit4 battery_too_low, bit5 always_on), item_kind u8, protocol u8, last_wake_result u8` (readers must accept longer values). `wake` writes of `0x01` below the battery floor fail with ATT error 0x80. `info` is ASCII `"<id>;<fw>"`. Config `ble_wake` (default true). `GET /ble` reports the advertising state. The app's connect flow becomes: BLE scan → write wake → join hotspot → HTTP, with the button as fallback.

## 3b. BLE fast lane (small requests without WiFi)

Most day-to-day sends are tiny (show, next, brightness, config, time, playlist, scene). They go over the
existing BLE link instead of raising the hotspot. The GATT service has two characteristics for it:

- `req` (write without response, chunked): the app writes a request as frames of up to `MTU−3` bytes. Frame byte 0 is a
  header: bit7 = first frame, bit6 = last frame, bits 0–5 = sequence (mod 64). The reassembled payload is
  `METHOD SP path LF [body]` in UTF-8, e.g. `POST /brightness\n{"value":200}`. Max 16 KB per request; one request in flight.
- `rsp` (notify, chunked the same way): `STATUS SP LF [body]`, e.g. `200 \n{"ok":true,...}`.
The device routes the payload through the **same handlers as HTTP** (identical status codes and JSON). Endpoints allowed on the
fast lane: everything except `PUT /assets/{id}`, `PUT /texts/{id}`, `POST /ota`, `GET /screenshot`, `GET /assets/{id}` and
`GET /batlog` (bulk transfers stay on WiFi; the device answers `413` for them over BLE). A fast-lane request does not start a
WiFi session and does not touch the session idle timer. The app uses the fast lane whenever no WiFi session is open and the
request is allowed; it falls back to the doorbell + hotspot path otherwise. Throughput target: a 2 KB playlist document in < 1 s
at a 185-byte MTU (iOS negotiates up to 512).

## 4. HTTP API

Base `http://192.168.4.1`. JSON bodies are UTF-8. Every JSON response is an object; errors are
`{"ok":false,"error":"<code>","message":"<human>"}` with 4xx/5xx. Success responses carry `"ok":true`.

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/status` | – | see below |
| GET | `/assets` | – | `{"ok":true,"assets":[{"id","size","sha256","width","height","frames","atlas":bool}]}` |
| PUT | `/assets/{id}` | raw `.hca`; header `X-Content-SHA256: <hex>` | `201 {"ok":true,"id","size","sha256"}`; `409` if hash matches an existing identical asset (treated as success by the app); `413` if no space; `422` if malformed |
| DELETE | `/assets/{id}` | – | `{"ok":true}` (also removes it from the playlist) |
| GET | `/assets/{id}` | – | raw `.hca` (for debugging / app re-download) |
| GET | `/playlist` | – | playlist JSON |
| PUT | `/playlist` | playlist JSON | `{"ok":true}`; unknown asset ids → `422` |
| GET | `/config` | – | config JSON |
| PUT | `/config` | partial config JSON (merge) | full config JSON |
| POST | `/time` | `{"epoch":<unix s>,"tz_offset_s":<int>}` | `{"ok":true}` |
| POST | `/show/{id}` | `{"duration_ms":<optional>}` | `{"ok":true}` — plays `id` now, then resumes playlist |
| POST | `/next` · `/prev` | – | `{"ok":true}` |
| POST | `/brightness` | `{"value":0-255}` | `{"ok":true}` (live preview; persist with `/config`) |
| GET | `/screenshot` | – | raw framebuffer, `Content-Type: application/octet-stream`, 536×240 RGB565BE (257,280 bytes) |
| POST | `/ota` | raw app image; `X-Content-SHA256` | `{"ok":true}` then reboot after 1 s |
| POST | `/session/end` | – | `{"ok":true}`; WiFi off within 1 s, display on |
| PUT/GET/DELETE | `/texts[/{id}]`, `PUT/GET /fonts/{id}`, `POST/GET /reader` | – | Reader mode (see §5c) |
| GET/DELETE | `/coredump` | – | raw crash dump from flash after a panic (WiFi only; `404` when none); `/status.resets.coredump` flags one |
| GET | `/scenes` | – | supported live scenes and their parameter ranges (see the `scene` item below) |
| GET | `/batlog` | – | `text/csv` battery log: `epoch,uptime_s,mv,pct,usb,mode,display,brightness` one row per minute, ring-buffered (~64 KB). Optional endpoint; `404` if the firmware lacks it |
| DELETE | `/batlog` | – | `{"ok":true}` clears the log |

Memory errors: any endpoint may answer `503 {"ok":false,"error":"no_memory"}` when internal RAM is exhausted,
and bulk uploads `503 low_memory` when fewer than 12 KB are free. Both are **retryable**: the app waits 2 s and retries up to 3 times.

`/status`:
```json
{"ok":true,
 "device":{"name":"PixelClip","id":"a1b2","fw":"0.1.0","hw":"ws-amoled-1.91","protocol":1},
 "battery":{"mv":3870,"pct":64,"charging":false},
 "storage":{"total":12582912,"used":1048576,"free":11534336},
 "playlist":{"count":4,"index":1,"current":"sunset-7f3a"},
 "time":{"epoch":1760100000,"tz_offset_s":7200,"synced":true},
 "session":{"idle_s":12,"timeout_s":120},
 "resets":{"wdt":0,"brownout":0,"panic":0,"rtc_wdt":0,"last":"usb_uart"},
 "power":{"usb_hold":true,"light_sleeps":0,"light_sleeps_while_usb":0,"awake_violations":0},
 "orientation":{"mode":"auto","flipped":false},
 "uptime_s":5400}
```
`battery.usb_present` is true when the USB port is active right now or the battery pin has read ≥ 4.25 V in 3 of the last 5
seconds; it clears within ~3 s of unplugging. `power.usb_hold` is true while USB is present (the clip never light-sleeps on USB; each ESP32-S3 light sleep detaches USB). `resets` counts reasons across boots (persisted); `rtc_wdt` > 0 means the
light-sleep watchdog had to recover the clip (see firmware/README.md "Light sleep on battery").

Playlist JSON:
```json
{"version":1,
 "items":[
   {"type":"asset","id":"sunset-7f3a","duration_ms":10000,"transition":"fade"},
   {"type":"asset","id":"cat-anim-2c1d","duration_ms":0,"loops":3,"transition":"cut"},
   {"type":"scene","scene":"snow","duration_ms":30000,"transition":"fade"}
 ]}
```
**Scrolling strips (marquees).** A text marquee pre-rendered as frames costs megabytes; instead the phone renders the whole message once as a single frame wider than the screen (`width` up to 8192, `height` 240, flag `is_strip`) and the device scrolls a 536-px window across it:
```json
{"type":"asset","id":"msg-hello-91ab","scroll":{"px_per_s":80,"direction":"left","gap_px":120,"loops":3},"transition":"fade"}
```
The device shows the strip entering from the right (for `left`), scrolls at `px_per_s` (10–400), inserts `gap_px` of black between repeats, and plays `loops` passes (or `duration_ms` if set). `direction` ∈ `left | right`. Strips are decoded once into PSRAM; each frame is a row-wise copy, so 30 fps is cheap. A strip uploaded without `scroll` plays as a still showing its first 536 px. `GET /assets` reports `"strip":true` and the width.

The `scene` item type renders **live on the device** and reacts to the accelerometer (gravity direction) and to motion:
```json
{"type":"scene","scene":"sand","params":{"palette":"amber","density":60},"duration_ms":60000,"transition":"fade"}
```
`scene` ∈ `sand | water | fire | balls | snow | lava` (the firmware reports the supported list in `GET /scenes` as
`{"ok":true,"scenes":[{"id":"sand","params":{"palette":["amber","ocean","forest","candy","mono"],"density":[10,100]}}, …]}`).
`params` is a flat object of strings/numbers/booleans; unknown keys are ignored, missing keys take defaults; booleans map to 1/0. **`GET /scenes` is the source of truth** for scene ids, palettes, parameter names, ranges and defaults (it also carries `name` and `defaults`); the sample above is illustrative. An optional `seed` (u32) makes a scene deterministic apart from its motion input. `duration_ms: 0` for a scene item means 60 s. The device's `/screenshot` shows the current simulated frame.

**Scheduling (the "tonight" queue).** Two additions to the playlist document let content appear at chosen times with no phone present:
```json
{"version":1,
 "items":[
   {"type":"asset","id":"sunset-7f3a","duration_ms":10000,"transition":"fade"},
   {"type":"scene","scene":"snow","duration_ms":30000,"from":"21:30","until":"01:00"}
 ],
 "queue":[
   {"id":"q-1","at":1760140800,"type":"asset","asset":"happy-bday-3c9a","duration_ms":45000,"transition":"fade"},
   {"id":"q-2","at":1760144400,"type":"scene","scene":"balls","params":{"palette":"candy"},"duration_ms":60000}
 ]}
```
- Item-level `from`/`until` are local times of day (`HH:MM`, using the device's `tz_offset_s`); an item outside its window is skipped by rotation. Windows may cross midnight. Omitted = always active.
- `queue[]` entries are one-shot interrupts: at `at` (unix seconds) the device fades to that content for `duration_ms` (default 60 s), then resumes the rotation where it was. Entries are sorted by `at`, fire once, and are remembered as done across reboots (keyed by `id`). If the device discovers an entry more than 10 minutes late (it was asleep or off), it skips it. A queue entry wins over a running `/show`. `type` is `asset | scene | reader | oracle | board` with the same fields as playlist items (an entry names its asset with `asset`, since `id` is the entry's own id).
- `GET /status` reports `"queue":{"pending":2,"next_at":1760140800,"done":1,"active":null}` and `"clock_ok":true` when time is synced (queue entries do not fire while `time.synced` is false; windowed items are treated as inactive while unsynced).
- Normative details (match the firmware): queue entries play **one at a time in `at` order**; an entry that comes due while another is playing waits, then plays its full `duration_ms`; an entry that would *start* more than 600 s late is skipped. Default transition for queue entries is `fade`. Limits: ≤ 64 entries, ids 1–40 printable characters, `clock`/`text` types not allowed in the queue. Nothing fires during an upload session (the panel is off); a due entry fires when the session ends if still within 600 s, else is skipped. Window strings are exactly `HH:MM`; `"24:00"` is accepted only as `until`; `from == until` is rejected (422). One missing bound means 00:00 / 24:00.

**Lone item rule**: when the active rotation has exactly one item it is held indefinitely with no re-transition: a still stays, an animation loops seamlessly, a strip scrolls endlessly (ignoring `loops`), a scene runs on, a reader reads to the end and holds its end card. `duration_ms` is ignored for a lone item (except reader). The app's default send is exactly this: one "Now" item; rotation and timing exist only when the Tonight planner adds them.

Rules: `duration_ms > 0` wins. If `0`, play `loops` complete loops (min 1) for animations, 5 s for stills.
`transition` ∈ `cut | fade` (fade = 250 ms brightness ramp down, swap, ramp up). An empty playlist shows the built-in idle screen.

Config JSON (all keys optional on PUT):
```json
{"name":"PixelClip","brightness":160,"upload_timeout_s":120,"ap_password":"pixelclip-2026",
 "low_battery_pct":8,"default_transition":"fade","tz_offset_s":7200,"orientation":"auto"}
```

### Orientation

A hair clip is worn on either side of the head, and on one side the board sits the other way up. The clip
therefore supports a **180° flip** of the whole screen (never 90°: the panel is landscape-only).

- Config `orientation` ∈ `auto | normal | flipped` (default `auto`, persisted).
- `auto`: the device flips when the low-passed display-frame gravity (§5b) has `gy < −0.5` (things fall
  towards the top edge of the screen) continuously for 1 s, and flips back when `gy > +0.5` for 1 s. In
  between (face-up on a table, on its side) it keeps the current orientation. Boot starts `normal` unless
  gravity already says otherwise. `normal` / `flipped` force one orientation.
- The flip is done by the panel (MADCTL), between frames: no framebuffer transform, no CPU cost, so every
  kind of content flips with it (assets, strips, scenes, reader, oracle, board, system screens). The
  framebuffer and `.hca` coordinates stay upright; a screenshot of the framebuffer is not flipped.
- **Live scenes are exempt**: they already answer to real gravity, so while a scene item shows the panel
  stays upright and the scene gets the true gravity vector; the decided orientation applies again with the
  next item. (`status.orientation.flipped` reports the decision, not the panel.) `GET /imu` keeps
  reporting the unrotated display-frame vector and adds `"flipped":true|false`.
- `/status` carries `"orientation":{"mode":"auto","flipped":false}`. A change of `orientation` over
  `PUT /config` applies immediately (also over the BLE fast lane).
- The app shows the setting as "Auto-rotate" (on = `auto`) with a manual "Flip screen" toggle when off,
  and the current state on the clip card.

## 5c. Reader (RSVP speed reading)

Inspired by RSVP Nano. The phone uploads plain text; the device shows one word at a time, centred on its
**optimal recognition point** (ORP), which is drawn in the brand accent while the rest of the word is white.

- Texts: `PUT /texts/{id}` (UTF-8 plain text, ≤ 1 MB, header `X-Content-SHA256`; same id rules as assets),
  `GET /texts` → `{"ok":true,"texts":[{"id","bytes","words","title","progress_word"}]}`, `DELETE /texts/{id}`.
  The first line of the file is the title. The device tokenises on upload and stores a word index.
- Fonts: a **reader font** is two glyph atlases rendered by the phone from the chosen typeface at 2 sizes
  (normal and compact for long words), each uploaded twice: white glyphs and accent glyphs (`is_glyph_atlas`),
  plus a font document `PUT /fonts/{id}` →
  `{"glyphs":"ABCDEF…","advance":[…],"cell_w":64,"cell_h":120,"baseline":92,"atlas_white":"…","atlas_accent":"…","compact":{…same keys…}}`.
  Glyph `i` of the atlas is `glyphs[i]` (UTF-8 string, so accented letters are supported); `advance[i]` is the
  pen advance in px. Missing glyphs render as the `?` glyph.
- Playlist/queue item: `{"type":"reader","text":"id","font":"id","wpm":300,"from_word":0,"loop":false,"duration_ms":0}`.
  Timing per word = 60000/wpm ms × a factor: ×1.3 for words ≥ 8 chars, ×1.6 for ≥ 12, +50 % after a comma/semicolon,
  +100 % at sentence end, and a 300 ms blank at paragraph breaks. The ORP index follows the Spritz rule
  (length 1 → 0, 2–5 → 1, 6–9 → 2, 10–13 → 3, else 4) and is pinned to screen x = 230 so eyes never move.
  A thin tick mark above and below the ORP column (2 px, dim) stays fixed.
- Controls: while a reader item is active the BOOT **short press pauses/resumes** (instead of "next"); a double
  press skips to the next playlist item. `POST /reader {"action":"pause"|"resume"|"seek","word":n}`; `GET /reader`
  → `{"ok":true,"text":"id","word":n,"words":N,"paused":bool,"wpm":w}`. Progress is persisted per text every 50 words
  and on pause, so the reading resumes where it stopped (`from_word` overrides it).
- At the end the device shows a small "fin · 1 234 words · 4 min" card for 3 s then resumes rotation (or loops).
- `/status.playlist.current` is `"reader:<id>"` while reading.

### 5c.1 Text layout (wrapping rules)

The clip lays out the text it draws itself (the Oracle's screens, §5f.2 onward) with one layout, `core/include/textlay.h`,
and a reader font (§5c: white + accent atlases, a font document with `normal`, optional `compact` and `large` faces).
The phone's virtual clip implements the same rules so both sides break lines identically. Normative:
- The text is UTF-8; at most 900 bytes are laid out. It is wrapped as one column at one face (the caller picks the
  face, e.g. §5f.11's largest face that fits) into at most 64 lines; beyond that the last line is cut so that it ends
  with "…", at a word boundary when that keeps at least 60 % of the line.
- Words are separated by whitespace (runs collapse; leading and trailing whitespace is dropped). A line feed in the
  text is a hard line break. No-break spaces (U+00A0, U+202F, U+2007) join and are drawn as a space.
- French punctuation stays with its word: a space before `! ? : ; » ” … ›` and after `« “ ‹` never breaks.
- A word wider than the line is broken after a hyphen, dash or slash (`-`, `/`, U+2010, U+2013, U+2014) if possible,
  else between glyphs.
- The space at a line break is not drawn.
- Each line is centred on its pen extent in the box: `x0 = floor((box_w − width) / 2)`; the line pitch is the face's
  `cell_h`. How many lines make a page, and where the block sits vertically, is up to the screen that uses the layout
  (§5f.11).

## 5f. Oracle (tarot)

A tarot oracle on the clip. The reading method follows *The Way of Tarot* (Jodorowsky & Costa); every text the clip
and the app show is original. The person holds a question in mind; the clip deals **three cards** and reads them for
that question in a few one-page screens, paged by hand. The first deck is the 22 trumps of Jean Dodal's Tarot de
Marseille (Lyon, 1701; public domain, BnF/Wikimedia). Cards are never reversed. The phone renders the card images,
the keyword tiles and the glyph atlases; the clip draws every text itself from a phrase bundle with those atlases and
composes the screens.

**What an oracle is made of** (one deck shared by every language; bundle, keys and fonts per language and text size):

| Part | Item field | Stored with | Format |
|---|---|---|---|
| phrase bundle `B` | `id` (`asset` in `queue[]`) | `PUT /texts/{id}` | UTF-8, 1 byte to 96 KB (the real bundles are ~80 KB); §5f.1, §5f.2 |
| body font | `font` | `PUT /fonts/{id}` | a reader font (§5c): `normal`, optional `large` and `compact` faces (§5f.11) |
| numeral font | `font_big` | `PUT /fonts/{id}` | optional; checked like `font`, but no current screen draws with it |
| deck `D` | `deck` | `PUT /assets/{id}` | `108×206` glyph atlas, `1 + cards` frames: 0 = the back, `1 + i` = card i (§5f.12) |
| keys `K` | `keys` | `PUT /assets/{id}` | optional `160×34` glyph atlas, `cards` frames: frame i = card i's keyword (§5f.12) |

Cards are numbered from 0 in deck order. The deck and the keys carry the glyph-atlas flag (§2 flags bit 0) and are not
strips.

**Item** (playlist `items[]`, `queue[]`, and the body of `POST /show/{id}`):
```json
{"type":"oracle","id":"tarot-reader-fr-3f2a","deck":"tarot-dodal-deck-9c1e","keys":"tarot-dodal-fr-keys-…",
 "font":"tarot-font26-…","cards":22,"shake_g":0.9,"face_ms":0,"page_ms":0,"hold_ms":300000,
 "duration_ms":180000,"transition":"fade"}
```

| Field | Rule | Default |
|---|---|---|
| `id` | required: the bundle's `/texts` id (a queue entry names it with `asset`, since its `id` is the entry's own) | – |
| `deck` | required: an asset id | – |
| `keys` | an asset id, or absent for no keyword row; `null` or a non-string is rejected | absent |
| `font` | required: a `/fonts` id | – |
| `font_big` | a `/fonts` id, or absent; it must exist, but nothing is drawn with it | absent |
| `cards` | required: an integer 3 … 78 (three distinct cards are drawn); fixes the deck's and the keys' frame counts | – |
| `shake_g` | a number 0.4 … 2.0: the shake that deals on *armed* (§5f.8) | 0.9 |
| `face_ms` | an integer 0 … 86 400 000: *three* turns by itself after this long; 0 = only by hand (§5f.3) | 0 |
| `page_ms` | an integer 0 … 86 400 000: the same for each *lean* and *detail* screen | 0 |
| `hold_ms` | an integer 0 … 86 400 000: the idle timeout back to *waits*; 0 = never (§5f.3) | 300 000 |
| `reader` | optional; when present it must be a string equal to `id` | – |
| `mode`, `daily`, `pages`, `notes` | accepted and ignored, whatever their value | – |

`duration_ms`, `transition` and `from` / `until` work as for any item: in a rotation `duration_ms` works as for a still
(0 = 5 s), a lone item holds (§4), and while a draw is in progress the item's end waits (§5f.8).

**Validation.** `PUT /playlist` checks an oracle item (or queue entry) in this order: a malformed field → 422
`invalid_playlist`; a bundle that is not stored → 422 `unknown_text`; a `font` or `font_big` that is not stored → 422
`unknown_font`; a `deck` or `keys` that is not stored → 422 `unknown_asset`; a deck or keys of the wrong size, kind or
frame count → 422 `invalid_playlist`; a bundle over 96 KB, without a `[prompt]` line, or without a `card.<i>.reading`
line for every `i < cards` → 422 `invalid_playlist`. A stored item that fails these checks when the playlist loads (for
example after its `font_big` was deleted, which does not remove the item) stays in the playlist and is skipped.
`POST /show/{id}` with an oracle body (the path names the bundle; a body `id` is ignored) applies the same checks, answering 404 `unknown_asset` for an unknown deck or keys and 422 `invalid_item` for anything else;
without a body it shows the first playlist item, then queue entry, whose bundle is `{id}` (404 `unknown_asset` when
none). Deleting the bundle, the body font, the deck or the keys removes the items that use it.
`/status.playlist.current` is `oracle:<bundle id>`.

**Screens.** `/status.oracle.state` names the screen on show; a tap is `POST /oracle/turn`, a double tap
`POST /oracle/back` (§5f.3):

| State | On screen | Tap | Double tap |
|---|---|---|---|
| `waits` | the back `D[0]` beside the `[prompt]` text (§5f.10) | → `armed` | nothing (the floor) |
| `armed` | the back beside `[prompt.armed]` (`[prompt]` when the bundle has none) | deals → `shuffle` | → `waits` |
| `shuffle` | 1.2 s of random cards in the three card slots, ending on A, B, C (§5f.6) | nothing | nothing |
| `three` | A, B, C and their keywords (§5f.12) | → the first lean screen, else the first detail, else `hold` | → `waits` |
| `lean` | one of five text screens, `page` 0–4 (§5f.7) | → the next lean screen, else the first detail, else `hold` | → the previous lean screen, else `three` |
| `detail` | a card's brief beside the card, `page` 0–2 = A, B, C (§5f.7, §5f.10) | → the next detail, else `hold` | → the previous detail, else the last lean screen, else `three` |
| `hold` | the *three* frame again | → `waits` | → the last detail, else the last lean screen, else `three` |

A lean screen without text and a card without a brief are skipped in both directions. A shake deals only on *armed*
(§5f.8); `POST /oracle/draw` deals from any screen (§5f.6). The hint arrow of §5f.11 shows on every screen but the
shuffle.

**Content.** The readings, keywords, briefs and phrase variants are the app's own texts, French or English per bundle,
and the app keeps them editable. The deck's images keep the card names as printed (LE MAT, LE BATELEVR, …). The clip shows the
row the way the method reads it: the cards, their keywords, a few short sentences; the phone shows the fuller reading
(the paragraph of §5f.1 and each card's `reading`).

### 5f.1 The sentence reader

What a practised reader would say about the row A B C, generated identically on the clip and on the phone from the
method's **rules** over a phrase bundle, never from published prose. The engine is `core/include/oracle_reader.h`; the
iOS mirror `ios/PixelClipKit/Sources/PixelClipKit/Tarot/SentenceReader.swift` reproduces it byte for byte against the
shared fixtures in `core/fixtures/tarot/` (`cases.json` for the paragraph, `cases-lean.json` for the lean screens). It
writes two things:
- the **paragraph** (`orr_compose`): the findings below, then the positions, then the closing, at most **900 bytes**. It
  has no screen on the clip: `/status.oracle.reading` carries it on *three* and *hold*, and the phone shows it;
- the **lean screens** (`orr_compose_lean`, §5f.7), built from the same sentences.

**Bundle format.** A UTF-8 text uploaded under `/texts` (the app names it `tarot-reader-<lang>-<hash>`), one per
language. Lines are split on LF (a trailing CR is dropped). `[name]` starts a section; a repeated header adds to it.
Ignored: blank lines (spaces and tabs only), lines before the first header, lines longer than 512 bytes, lines that are
not valid UTF-8 or carry a control byte other than TAB, and unknown sections.
- **Phrase sections** hold one variant per line (6–8 in the real bundles): `positions`, `echo`,
  `arc.rising|falling|peak|dip|plateau|still`, `gaze.facing|back|follow|front|center.left|center.right`, `kin.sum21`,
  `kin.same`, `step.up|down|restart`, `place.wheel.first|later`, `place.world.first|last`, `place.fool.before|after`,
  `hsum`, `hsum.drawn`, `row.open.left|open.right|closed`, `short.card`, `short.positions` (§5f.4), and the pair
  sections `couple.<a>-<b>`, `couple.<a>-<b>.any`, `meet.<a>-<b>`, `kin.sum21.<a>-<b>`, `kin.same.<a>-<b>`,
  `succ.<a>-<b>` (card indices of one or two digits, a ≠ b, below 78).
- **Placeholders**: `{W.f}` with W one of `q A B C X Y S` and f one of
  `name kw num role from to closing question srole`, and `{tag}`. A variant with any other placeholder, or with a `{`
  never closed, is ignored. `{A}` `{B}` `{C}` are the row (a pair finding binds `{A}` and `{B}` to its pair), `{X}` is the
  card a finding names, `{S}` the hidden sum's card, `{tag}` an echo's tag gloss; `{q.*}` and `{Y.*}` are always empty.
  `{X.srole}` is the card's `srole` line, else its `role`.
- **One-line sections** (the first usable line counts): `card.<i>.<field>` (the per-card table below), `tag.<name>` (a
  symbol tag's gloss), `depth` (the words appended after a second-row card's keyword in arc sentences: "en profondeur" /
  "in depth"), `prompt` and `prompt.armed` (§5f.8), `question.lead`, and `hint.waits|armed|next|back|end` (§5f.9).

**Per-card table**, one `[card.<i>.<field>]` section per field, per language:

| Field | Content |
|---|---|
| `name` | the card's name in sentences |
| `kw` | its keyword |
| `num` | the Marseille numeral: "0" for Le Mat, "XII" for the card printed IIX |
| `degree` | 1–10; Le Mat 0, Le Monde 21 |
| `row` | 1 or 2; 0 for Le Mat, 3 for Le Monde |
| `gaze` | `left`, `right` or `front`: where the main figure looks, read from the card as printed |
| `role` | what the card is, as a noun phrase ("une énergie qui cherche où aller") |
| `srole` | optional shorter role for the lean screens (§5f.4) |
| `from` | the card as the one the person comes from ("d'une longue attente") |
| `to` | the card as the one the person goes towards ("vers une parole qui enseigne") |
| `closing` | the line the centre card leaves the person with |
| `symbols` | 2–4 tags, comma-separated, from: water, sun, moon, animal, tower, crown, book, sword, cup, coin, staff, child, angel, star, wheel, hand, path, flower, egg, mountain |
| `brief` | the card's detail screen (§5f.7) |
| `reading` | the card's full reading: required for every card, shown by the phone |
| `printed`, `question` | parsed; no current screen uses them |

**Numbers.** number(i) is 0 for Le Mat (row 0), 21 for Le Monde (row 3), the degree in row 1 and the degree + 10 in
row 2. In sums Le Mat counts 22, and reduce(x) sums the digits of x until x ≤ 22. The arc compares the
`degree` lines, 21 counted as 11.

**Findings.** Pairs are scanned (A,B), (B,C), (A,C) ("the scan"); "adjacent" means (A,B) then (B,C). Each finding is
written at most once (facing / back once per adjacent pair). In this order, which is also descending strength:

| Finding | Strength | Rule |
|---|---|---|
| couple | 5 | the first pair of the scan with a section: `couple.<x>-<y>` in the row's order ({A} = x, {B} = y), else `couple.<lo>-<hi>.any`. That pair is "the couple's pair". The method's principal couples: Le Mat–Le Monde, Le Bateleur–La Force, La Papesse–Le Pape, L'Impératrice–L'Empereur, Le Chariot–L'Étoile, La Justice–L'Hermite, La Lune–Le Soleil |
| encounter | 4 | the first pair of the scan with `meet.<x>-<y>` ({A} = x, {B} = y), else with `meet.<y>-<x>` ({A} = y, {B} = x). The method's encounters between human figures, plus Bateleur–Justice, Bateleur–Lune, Force–Empereur, Force–Pape, Force–Chariot, Force–Hermite, Force–Soleil, Pape–Justice, Empereur–Justice, Chariot–Justice, Étoile–Soleil, Justice–Soleil; a bundle may carry one or both orders |
| centre gaze | 4 | B looks left: `gaze.center.left` (B addresses A); right: `gaze.center.right` (B addresses C); front: `gaze.front` (B looks at the person) |
| facing / back to back | 3 | for each adjacent pair: the left card looks right and the right card left → `gaze.facing`; the reverse → `gaze.back` ({A}, {B} = the pair). A pair the written centre-gaze sentence covers (left: (A,B); right: (B,C)) is skipped, so `gaze.facing` reads only in bundles without `gaze.center.*` |
| kinship | 3 | outside the couple's pair: the first pair of the scan whose numbers sum to 21, else the first pair of one degree with one card in row 1 and one in row 2: `kin.sum21.<lo>-<hi>` / `kin.same.<lo>-<hi>` ({A} = lo, {B} = hi), else the generic `kin.sum21` / `kin.same` ({A} = x, {B} = y) |
| succession | 3 | the first adjacent pair with `succ.<x>-<y>` ({A} = x, {B} = y): the method's named successions (XII→XIII, XIII→XIIII, XV→XVI, XVI→XVII, XX→XXI, X→XI, X→I and their reverses, as the bundle provides) |
| step | 2 | the first adjacent pair, both in rows 1–2, neither the couple's nor the succession's pair, whose degrees go 10 → 1 (`step.restart`), d → d+1 (`step.up`) or d → d−1 (`step.down`) and whose section has a variant ({A} = x, {B} = y) |
| arc | 2 | the shape of the degrees: `arc.still` (all equal), `arc.plateau` (two equal), `arc.rising`, `arc.falling`, `arc.peak` (B highest), else `arc.dip`; a second-row card's `{X.kw}` gets " " + `[depth]` |
| placement | 2 | the first of: La Roue de Fortune (card 10) in A → `place.wheel.first`, in B or C → `place.wheel.later` ({X} = card 10); Le Monde (card 21) in A → `place.world.first`, in C → `place.world.last` ({X} = card 21); Le Mat in A or B → `place.fool.before` ({X} = the next card), in C → `place.fool.after` ({X} = B); the Le Mat sentences are skipped when Le Mat and {X} are the couple's pair |
| hidden sum | 2 | S = reduce(n(A) + n(B) + n(C)) mod 22, each number with Le Mat counted 22 (a result of 22 becomes 0, Le Mat): `hsum.drawn` when S is A, B or C, else `hsum` ({S} = S) |
| open / closed | 1 | A looks left: `row.open.left`; else C looks right: `row.open.right`; else A looks right and C left: `row.closed` |
| follow | 1 | the first adjacent pair not already covered, both looking the same way: `gaze.follow` ({A} = the follower, the card whose gaze points at the other) |
| echo | 1 | the first tag, in the fixed order of the list above, carried by two or three of A, B, C that has a `[tag.<name>]` gloss: `echo` |

The paragraph is the findings in that order, then `positions`, then the closing (the `card.<B>.closing` line itself),
joined with one space. Each sentence is cut to 960 bytes at a UTF-8 boundary.

**Variants.** The variant of a section is `fnv1a32` (offset 2166136261, prime 16777619) over the bytes
`-1,A,B,C,<section>` (decimal; e.g. `-1,2,11,19,arc.dip`, `-1,4,3,9,couple.4-3`) mod the number of valid variants, in
bundle order; a section without a valid variant writes nothing. The same row therefore always reads the same way on
the clip and on the phone.

**Budget.** While the paragraph is over 900 bytes the weakest finding goes first, and of equal strengths the one written
later: echo, follow, open / closed; at strength 2 the arc first loses its numerals (every `" (…)"` / `"(…)"` group, as
the regex ` ?\([^)]*\)`), then hidden sum, placement, arc and step go; then succession, kinship, the second facing /
back sentence and the first; then centre gaze and encounter; then the couple. The positions and the closing are never
dropped; if they alone are too long the text is cut before the last space that keeps at most 897 bytes (else at a
UTF-8 boundary) and "…" is appended (never with the real bundles).

**Wording rules for bundle texts.** In pair sections `A` and `B` are the two cards of the pair (in `gaze.follow` A is
the follower, in `gaze.front` B is the card looking out). In arc sentences every numeral sits inside parentheses, so
the budget can remove them. No template puts "de" / "à" before a name. No death, ruin or punishment vocabulary next to
XIII, XV, XVI; no "tu dois" / "you must"; no future tense about events; no reversed-card language.

**Memory.** The clip reads the bundle into PSRAM and indexes it in an arena of `orr_arena_bytes()` (about 1 KB + 8 bytes
per variant line + 17.3 KB of compose scratch: ~25 KB for the real bundles).

### 5f.2 Text drawn from the bundle

The clip draws every oracle text itself, from the item's bundle with its body font; no text image is uploaded.
- *waits*: `[prompt]` ("Pense à ta question, puis appuie." / "Hold your question, then press."). An item whose bundle
  has no `[prompt]` line is rejected.
- *armed*: `[prompt.armed]` ("Secoue le jeu." / "Shake the deck."), else `[prompt]`.
- *lean*: the five screens composed for the draw (§5f.7).
- *detail*: the card's `card.<i>.brief`.

Every card must have a `card.<i>.reading` line (checked when the item is validated); the phone shows it, the clip does
not. `[question.lead]`, `card.<i>.printed`, `card.<i>.question` and the `[hint.*]` words (§5f.9) are parsed but not
drawn. Each text is laid out with the wrapping rules of §5c.1 in the boxes of §5f.10 and §5f.11, in the largest face
that fits.

### 5f.3 Paging by hand

The clip has one usable button (BOOT; the other is the hardware reset) plus the shake, so the oracle is paged by hand:
- **Tap** = the next screen; **double tap** (two taps within 350 ms) = the previous screen (the table of §5f). While an
  oracle item is on screen a single tap therefore acts 350 ms after release, and neither advances the playlist; outside
  an oracle a tap is "next item" at once. The long presses keep their meaning (§3).
- `POST /oracle/turn` is a tap and `POST /oracle/back` a double tap (§5f.6); the app's virtual clip and the end-to-end
  tests use them.
- **Timers.** `face_ms` (on *three*) and `page_ms` (on each *lean* and *detail* screen) are 0 by default: nothing
  advances by itself. A non-zero value turns that screen after that long.
- **Idle timeout.** With no tap, double tap or draw for `hold_ms` (default 300 000 = 5 min; 0 = never), any screen
  but *waits* returns to *waits*.
- **Text size** (the app). Small / Medium / Large set the body font at 18 / 22 / 26 pt, its `large` face at 1.3× that
  (§5f.11), its `compact` face at 12 pt, and `font_big` at 48 / 56 / 64 pt. The size is part of the font ids, so the sizes
  coexist on the clip. The virtual clip lays out identically.

### 5f.4 The short lines

The lean screens' first two lines (§5f.7) speak the row **by card** and **by position**:
- `[short.card]` variants use `{X.num} {X.name} {X.srole}` ("{X.num} {X.name} : {X.srole}." → "XIIII Tempérance : la
  guérison, la mesure."). The by-card screen picks **one** variant per row, hashed as `-1,A,B,C,short.card`, fills it
  for A, B and C in turn ({X} = the card) and joins the three lines with one space, so the punctuation is uniform.
- `[short.positions]` variants use `{A.from}`, `{B.name}`, `{B.srole}`, `{C.to}` ("Tu viens {A.from} ; au centre,
  {B.name}, {B.srole} ; tu vas {C.to}.").
- `card.<i>.srole` is optional; without it `{X.srole}` is the card's `role`.

### 5f.5 The question

The question is always the person's own and is never shown: there is no question card, and every closing is the centre
card's (§5f.6).

### 5f.6 One reading: the draw, the routes, the status

**The draw.** A, B and C are three distinct cards of the item's `cards`, drawn at random (an xorshift32 the clip seeds),
never the same set as the previous draw (in any order) when `cards` > 3, or the row `POST /oracle/draw` forces. They are
read for the person's question: A where the person comes from, B the centre, C where the person goes. The shuffle lasts
1200 ms at 12 fps: shuffle frame k = floor(t × 12 / 1000) shows, for k = 0 … 13, a random card in each of the three
slots (never that slot's previous shuffle card nor its chosen one), and from 1166.7 ms the chosen A, B, C; no keywords.
Then *three*.

**Routes** (fast lane allowed, §3b; the body of each answer is `{"ok":true}` plus the fields of `/status.oracle`):

| Method | Path | Body | Effect |
|---|---|---|---|
| POST | `/oracle/draw` | optional `{"cards":[a,b,c]}` | a draw now, from any screen (→ *shuffle*). `cards` forces the row: three distinct integers 0 … `cards`−1, else 422 `invalid_cards`; without it (or `null`) the row is random. Other keys are ignored |
| POST | `/oracle/turn` | – (ignored) | a tap |
| POST | `/oracle/back` | – (ignored) | a double tap |

All three answer 409 `not_showing` when no oracle item is on screen or the panel is off (an upload session with the
display off), and 500 `busy` when the player does not answer.

**`/status.oracle`**, always present:
```json
"oracle":{"cards":22,"state":"lean","cards_drawn":[3,11,19],"card":-1,"page":2,"reading":"…"}
```
- `cards`: the item's `cards`; 0 when no oracle item is current (then `state` is `"waits"`, every number −1 and
  `reading` `""`).
- `state`: `waits | armed | shuffle | three | lean | detail | hold`.
- `cards_drawn`: A, B, C from *three* on (*three*, *lean*, *detail*, *hold*); −1 each on *waits*, *armed* and *shuffle*.
- `card`: on *detail* the card whose brief shows; −1 otherwise.
- `page`: on *lean* the screen 0–4; on *detail* 0–2 (A, B, C); −1 otherwise.
- `reading`: on *lean* that screen's text; on *detail* the card's brief; on *three* and *hold* the paragraph (§5f.1);
  `""` otherwise.

### 5f.7 The lean draw

After *three* come up to five **lean** screens and up to three **detail** screens, each one page, then *hold*. The method's
two cores, the numbers read as a path and the relationships between the cards, each keep a screen. The lean screens
(`orr_compose_lean`, in `page` order):

0. **By card**: the `[short.card]` line for A, B and C (§5f.4).
1. **By position**: a `[short.positions]` variant (§5f.4).
2. **By the numbers**: the arc sentence (§5f.1, with its numerals and `[depth]` words).
3. **Together**: the strongest finding of §5f.1's order (before any budget) other than the arc, `gaze.front`,
   `gaze.follow` and echo: couple, encounter, centre gaze (left or right), facing / back, kinship, succession, step,
   placement, hidden sum or open / closed. Empty (so skipped) when there is none.
4. **And**: the second such finding + " " + `{B.closing}` when that fits one page, else the finding alone when it
   fits, else `{B.closing}` alone; `{B.closing}` alone when there is no second finding.

A screen whose section has no variant is empty and is skipped. **Detail A, B, C**: one page per card from
`card.<i>.brief` (at most 140 characters in the app's bundles: the numeral and name first, the degree and its stage in
the method's terms, what the printed figure does, what the card asks), beside the card (§5f.10); a card without a brief
line has no detail screen.

"Fits one page" (the *and* screen) is the composer's page test: on the clip and in the app the body font's `normal` face
in the full-width box (§5f.11); in the fixtures (`core/fixtures/tarot/cases-lean.json`) at most 150 code points.
Each screen is then drawn in the largest face that fits (§5f.11); a text longer than a page even in the `compact` face
is cut (the app's bundles keep every lean text within one page).

### 5f.8 Arming, and no interruptions

- **Arming.** On *waits* a shake does nothing. A **tap** on *waits* arms the deck (*armed*: the back with
  `[prompt.armed]`). A **shake** on *armed* deals (→ *shuffle*); a tap on *armed* also deals (for a clip lying on a
  table); a double tap disarms (→ *waits*); *armed* times out to *waits* after `hold_ms` like every screen.
- **The shake** is a motion metric ≥ `shake_g` and is edge-triggered: it is ready again only once the metric has gone
  below `shake_g` / 2. On *armed* it wins over a press in the same step. On every other screen it is ignored (the edge
  is used up all the same): the only way to a new draw is back to *waits* (a tap on *hold*, double taps, or the idle
  timeout), then a tap, then a shake; or `POST /oracle/draw`. Without an IMU only taps and `POST /oracle/draw` deal.
- **No interruptions while a draw is in progress** (any state but *waits*, *armed* included): the item's end
  (`duration_ms`), queue entries and the playlist's time windows are **deferred** until the oracle is back at *waits*;
  then they act at once if still due (a queue entry more than 10 minutes late is skipped, as always). `/show`, a new
  playlist and `POST /queue/test` still take effect at once. Taps inside a draw never advance the playlist.

### 5f.9 The BOOT corner

The two side buttons sit at the USB end, one on each long edge: with the picture upright and the USB end on the
right, BOOT is the **top-right** button and the hardware reset the bottom-right one. Every oracle screen is laid out
around the **corner where BOOT is**, in framebuffer coordinates (the panel flip keeps the framebuffer upright for the
viewer): **top-right** normally, **bottom-left** when the panel is flipped (`display_is_flipped()`). The hint
(§5f.11) sits in that corner, and the card of *waits*, *armed* and *detail* sits at the other end (§5f.12). The
firmware repaints the oracle when the orientation changes, so the hint and the layout move live.

- The bundles carry word hints, `[hint.waits]` "appuie" / "press", `[hint.armed]` "secoue" / "shake", `[hint.next]`
  "suite" / "next", `[hint.back]` "retour" / "back", `[hint.end]` "fin" / "end"; the clip does not draw them (the
  hint is the triangle of §5f.11).

### 5f.10 A card beside its text

Screens that show one card with text (*waits*, *armed*, *detail*) put the card at the end away from the BOOT corner
(§5f.12) and the text in the box beside it (§5f.11).

- *waits* / *armed*: the back, with the prompt beside it.
- *detail*: the card, with its brief beside it in the largest face that fits that box on one page (§5f.11); when even
  the `compact` face does not fit, the card is left out and the brief takes the full-width box. Both sides' one-page
  tests check every brief beside the card at the three sizes (the fallbacks are allowed but reported).
- States, taps, timings, `/status.oracle`, the bundles and the fixtures do not depend on the layout.

### 5f.11 The hint, and text as big as fits

- **The hint is one ▶**: a filled triangle **8 px wide × 9 px tall** (rows 1, 3, 5, 7, 9, 7, 5, 3, 1 px, clipped to 8)
  in the accent colour, in the **BOOT corner**, pointing at the button: normally its right edge 8 px from the right
  screen edge and its top row at y 4, pointing right; flipped its left edge 8 px from the left screen edge and its
  bottom row at y 235, pointing left. It shows on every oracle screen but the shuffle, including *armed* and *hold*
  (it always means "press to go on"). The **corner reserve** is the 24 × 16 px box around it (x 512…535, y 0…15
  normally; x 0…23, y 224…239 flipped); nothing else is drawn there.
- **Text boxes** are **224 rows** tall, clear of the corner reserve: rows **16…239** normally, rows **0…223** flipped.
  Full-width text (the lean screens, and *detail* without its card) uses
  **x 8…528**; text beside a card (§5f.10) uses **x 124…528** normally and **x 8…412** flipped (8 px from the 108 px
  card; box x ranges are end-exclusive, rows inclusive). Lines are centred in the box (§5c.1).
- **As big as fits.** The body font (§5c document) may carry a third face **`large`** (same keys as `normal`); the
  app renders it at 1.3× the chosen size (Small 18 → 23, Medium 22 → 29, Large 26 → 34 pt; compact stays 12 pt).
  Every text screen is laid out in the **largest face that fits its box on one page**: `large`, else `normal`, else
  `compact`. A font without `large` starts at `normal`. Reader mode ignores `large`. The one-page tests report, per
  size, how many screens land on each face.
- **The composer's one-page check** (the *and* screen's length, §5f.7) does not depend on the face chosen to draw a
  screen: it is the `normal` face in the full-width box of the normal orientation (520 px × 224 rows) on both sides,
  so clip and phone compose byte-identical text.

### 5f.12 The deck, the keywords and the card slots

- **Deck `D` frames are 108×206**; frame 0 is the back. A deck of another size → 422 `invalid_playlist`.
- **Keys `K` are 160×34**, frame i = card i's keyword, optional: absent → no keyword row. Each keyword's ink stays
  inside a **140×28 box at offset (10, 2)** in its tile. The app renders every keyword of a language at **one size,
  the largest** at which the longest keyword's ink fits 140 px wide and its line 28 px tall (Playfair Medium Italic,
  about 21 pt). The tiles have no background.
- ***three* / *hold* / *shuffle***: cards A, B, C at **y 0**, x **52, 214, 376**; keys `K[A]`, `K[B]`, `K[C]` at
  **y 206**, x **26, 188, 350** (card and key centres 106, 268, 430), the same in both orientations. Keys are pasted
  whole; at this pitch (162 px) the tiles do not overlap, and the corner reserve (§5f.11) stays clear in both
  orientations (card C ends at x 483, key C at x 509, key A starts at x 26).
- ***waits* / *armed* / *detail***: the back or the card at **y 17** (vertically centred), **x 8** normally and
  **x 420** flipped (the end away from the BOOT corner), with the text box of §5f.11 beside it.

## 5b. Live scenes (`core/include/scene.h`)

Live scenes run on a coarse simulation grid (default 134×60, i.e. 4× pixel scale; `balls` renders at full
resolution) and are stepped at the frame rate with the gravity vector `(gx, gy, gz)` in g, in the display's
frame of reference (+x to the right of the screen, +y down, +z out of the glass). The vector is the **direction things fall**: a clip worn upright reads about (0, 1, 0), lying face-up about (0, 0, −1). The firmware converts the IMU's specific-force reading and mounting orientation into this frame. `sand`, `water`, `snow` fall along
gravity and pile/flow; `fire` and `lava` rise against it; `balls` bounce off the four edges with restitution and get a
velocity kick from sudden accelerations. Rendering writes RGB565BE into the framebuffer and reports a dirty rect.

### 5b.1 Words: text that bounces with the movement

A few written words that bounce around as the clip moves, large enough to read: a live scene whose sprites
are the words, rendered big by the app; the clip moves them with the IMU.

- **Item**: `{"type":"scene","scene":"words","id":"<sheet>","params":{"bounce":60},"duration_ms":60000,"transition":"fade"}`
  in `items[]` and `POST /show`; in `queue[]` the sheet is named by `"asset"` (an entry's `id` is the entry id).
  `id` (required for `words`, ignored for other scenes) names the **sheet**:
  an `.hca` asset of `N` frames (1 ≤ N ≤ 12), all the same `w × h` (w ≤ 536, h ≤ 240, N·w·h ≤ 514 560 pixels), one
  **word per frame**, drawn in any colours on **black; black (0x0000) is transparent**, uploaded with the **atlas
  flag** (header flags bit 0) since it is not 536×240. `seed` as for other scenes. `POST /show` without a body shows a
  sheet that a words item or queue entry uses as that scene (the borrow rule of the oracle's bundle).
  Missing or non-`.hca` `id`, wrong sizes, or an unknown asset → 422 `invalid_playlist` (`unknown_asset` when the
  asset is absent, like the oracle's deck). Deleting the sheet drops the item. `playlist.current` = `scene:words`.
- **Words**: at item start the scene finds each frame's tight bounding box of non-black pixels; a frame with no ink is
  skipped (all black → the scene shows black and the firmware logs it). Each word is an **axis-aligned rectangle**
  that never rotates (text stays upright).
- **Physics** (pixels and seconds, sub-stepped like `balls`): gravity from the IMU scaled so 1 g crosses the screen
  height in ~0.6 s; bounces off the four edges with restitution `bounce`/100; word–word collisions as rectangles
  (positional separation on the axis of least penetration plus an impulse along it, no rotation); sliding/rolling
  friction so the words come to rest, side by side or stacked, when the clip is still — readable at rest; a sudden
  acceleration (shake) kicks every word like `balls`. Start positions spread the words over the screen from the
  seed; they fall in. Deterministic for a seed and an input sequence.
- **Orientation**: unlike the other scenes, `words` **follows the decided orientation** (§4 Orientation: it flips with
  the panel) because text must read upright; it receives the gravity vector expressed in the *flipped* display frame
  (gx and gy negated) when flipped, so the words still fall towards the physical bottom.
- **Rendering**: black ground; every word's sprite pixels composited at its integer position (black pass-through);
  the dirty rect is the union of the words' previous and current rectangles.
- **Params**: `bounce` INT 0…100, default 60. (Colour and size are baked into the sheet by the app.) `GET /scenes`
  lists `words` like the others.
- **App (Write)**: a switch "Bounce around" (the words move with the clip). Each word of the text is one frame,
  drawn with the chosen look (Bold, Script, Typewriter, DOTS) in that look's colour, at the **largest size** such that
  the cap height ≤ 72 px, the widest word ≤ 360 px, the line height ≤ 96 px and the words' total ink area ≤ 45 % of
  the screen (so they can move); at most 12 words (the text box says so and stops there). Frames are the largest word
  box plus 2 px, words centred. Sheet id `words-<hash of text, look, size>`; uploaded like any picture; the item goes
  to Now or the playlist like any Write. The phone's preview shows the words resting along the bottom edge (the
  virtual clip renders that still; the physics is not mirrored).

## 5g. Board: a list of timed rows that scrolls

A *board* is a generic list of timed row pictures: for example a timetable, the rest of today's agenda, or a list of
departures. The clip has no internet: the sender draws the rows and pushes them; the clip stacks them, **drops each
row by its own clock once its time has passed**, and scrolls slowly when the list is taller than the screen. The clip
knows nothing about what the rows mean.

- **Item**: `{"type":"board","id":"<sheet>","header":0,"empty":1,"rows":[{"frame":2,"until":1761062400},…],
  "scroll_px_s":16,"duration_ms":60000,"transition":"fade"}` in `items[]` and `POST /show` bodies; in `queue[]` the
  sheet is named by `"asset"` (as §5b.1). `id` names the **sheet**: an `.hca` of `N` frames (1 ≤ N ≤ 48), all the
  same `w × h` (w ≤ 536, 16 ≤ h ≤ 240, N·w·h ≤ 1 048 576 pixels), uploaded with the atlas flag (bit 0) unless it is
  536×240. Frames are opaque pictures (no transparency).
- `rows[]` (1…47 entries, in display order): `frame` (0…N−1) and an optional `until` (unix seconds): the row is shown
  while the clip's clock is before `until`; without `until` always. A frame may be used by several rows.
  `header` (optional frame): drawn fixed at the top, never scrolls, no `until`. `empty` (optional frame): drawn alone
  under the header when no row remains. While the clock is not synced (`/status.time.clock_ok` false) every row shows.
- **Layout**: rows centred horizontally (x = (536 − w) / 2), stacked with no gap below the header (or from y 0). When
  the stack is taller than the space left, it **scrolls up continuously** at `scroll_px_s` px/s (default 16, range 4…60),
  looping with a 48 px black gap; otherwise it is static. The row set is re-evaluated once a second; a row that expires
  disappears at the next loop boundary (static lists: at once). The board flips with the panel like a picture.
- **Validation** (422 `invalid_playlist` unless noted): missing/invalid `id`, absent sheet (`unknown_asset`), wrong
  sheet geometry or count, a `frame` out of range, `rows` empty, `until` not an integer, `scroll_px_s` out of range.
  Deleting the sheet drops the item. `playlist.current` = `board:<sheet>`. Rendering runs at ≤ 30 fps only while
  scrolling.

## 6. `core/` C API

`core/` is a dependency-free C11 library compiled into the firmware (as an ESP-IDF component) and into a
macOS test harness. Headers in `core/include/` are part of this contract.

- `hca.h`: parse header/frame table from memory, decode one frame (raw or RLE16) into a caller-provided
  RGB565BE buffer, optionally clipped; constant memory, no malloc (§2).
- `rsvp.h`: Reader mode (§5c): tokenising, word timing and the ORP, reader fonts (glyph-atlas pairs) and painting.
- `textlay.h`: text layout with a reader font, the wrapping rules of §5c.1.
- `scene.h`: live, motion-reactive scenes, `words` included (§5b, §5b.1).
- `oracle.h`: the tarot oracle's draw, screens, state machine and layout (§5f).
- `oracle_reader.h`: the sentence reader / composer over a phrase bundle (§5f.1, §5f.4, §5f.7).
- `oracle_text.h`: the oracle's text screens drawn from glyph atlases (§5f.2, §5f.10, §5f.11).
- `board.h`: which board rows show, where, and the scroll (§5g).

## 7. Versioning

`protocol` in `/status` is `1`. The app refuses to talk to a higher major and prompts for a firmware
update if the clip is lower than the app's minimum.
