# PixelClip firmware (ESP-IDF v5.5)

Firmware for the Waveshare ESP32-S3-AMOLED-1.91 (non-touch) worn as a hair clip. It plays a
playlist of `.hca` images/animations, scrolling strips (marquees), live motion-reactive scenes, Reader mode (RSVP
speed reading of uploaded texts), a tarot Oracle and boards (lists of timed rows), runs a "tonight" schedule (time windows + one-shot queue), and is managed over a WiFi hotspot that a long press or
the phone (BLE "doorbell") opens; the content keeps playing while it is up. Contract: `docs/PROTOCOL.md`.
Hardware facts: `docs/HARDWARE.md` (§8 there describes the old 220 mAh cell: the clip now runs on a
500 mAh / 0.5 A cell).

## Build, flash, monitor

```sh
source ~/esp/esp-idf/export.sh
cd firmware
idf.py set-target esp32s3        # once; sdkconfig is generated from sdkconfig.defaults (not committed)
idf.py build                     # fetches esp_lcd_sh8601, joltwallet/littlefs, mdns on first run
ls /dev/cu.usbmodem*             # native USB Serial/JTAG (no UART bridge on this board)
idf.py -p /dev/cu.usbmodemXXXX flash monitor
```

If the board does not show up, hold BOOT, tap RESET, release BOOT (ROM download mode), flash,
then press RESET. Exit the monitor with `Ctrl-]`.

Tunables live in `idf.py menuconfig` → **PixelClip** (QSPI clock, bounce-band rows, SoftAP
channel and TX power caps on USB / battery, RTC watchdog timeout, the bench light-sleep soak, CPU min/max MHz,
light sleep on/off, battery sample period) and
**PixelClip IMU (QMI8658C)** (enable, axis flips/swap = fallback when no bench calibration is stored, low-power ODR).

## Using the clip

| Button (BOOT) | Action |
|---|---|
| short press (< 0.4 s) | next playlist item — **except while a reader item is on screen**: pause / resume (a small "⏸" appears top right), and **while an oracle item is on screen**: draw / turn (see "Oracle"; it never advances the playlist). Also works during a screen-on upload session (ignored in a panel-off one). |
| double press (two short presses, releases ≤ 400 ms apart) while a reader item is on screen | next playlist item (the single-press pause therefore acts 400 ms after the release) |
| long press (1.5–6 s, acts on release) | enter / leave upload mode (also while reading). Leaving also suspends `wifi_always_on` until the next boot. |
| hold ≥ 6 s | "bye" for 1 s, display off, deep sleep; press BOOT to wake (= reboot) |
| short press while the clip shows "Update?" | allows a firmware update for 120 s ("Update allowed"); that press does nothing else. The prompt appears for 60 s when a client asks (`POST /ota/ask`, or a refused `POST /ota`), also in a panel-off session (the panel wakes for it). See "Firmware update permission". |
| five short presses within 3 s, then a long press within 10 s | puts the hotspot passphrase back to the factory default `pixelclip-2026` (for a lost phone; before, only erasing the flash over USB did that). The fifth press shows "Reset WiFi password?" / "hold to confirm"; the long press shows "WiFi password reset", saves it and ends a running session (an always-on hotspot restarts with the default), without toggling upload mode. Any other press, or 10 s, cancels (that press does nothing else); the five presses do their usual thing. Content, playlist and other settings stay. |

Upload mode (long press, or the BLE doorbell): the "WiFi: PixelClip-XXXX" splash for **2 s** while the SoftAP
comes up (WPA2, passphrase from config, default `pixelclip-2026`, channel 6, 1 station, TX capped at 10 dBm on USB / 8 on battery,
802.11g/n HT20), then **the content keeps playing** with a small connection dot in the top-right corner
(see "Screen-on upload sessions"). With `display_during_upload: false` the old behaviour applies: splash
3 s, then the panel sleeps (0x28 + 0x10) for the whole session. The session ends after `upload_timeout_s`
without a request, on `POST /session/end`, on another long press, on a BLE `wake` 0x02, or if the battery
drops below 3.5 V — except with `wifi_always_on`, where only the last three end it. After a long press, or
after any panel-off session, a "Done" screen shows for 1 s and the playlist resumes with a fade-in; a
screen-on session ended by the app or the timeout just loses its dot. The radio is off outside sessions
(`esp_wifi_stop`); the WiFi driver stays initialised while BLE runs and is deinitialised only with BLE off (see
"Light sleep on battery"). Bluetooth (NimBLE) runs the doorbell unless `ble_wake` is false (then it is never
initialised). On battery below 3.9 V a session runs with the panel off, TX is capped at 8 dBm, and a sag only
ends the session (see "Light sleep on battery").

## Screen-on upload sessions (config `display_during_upload`, default true)

- **Flow.** Long press / BLE wake → the player stops, "WiFi: PixelClip-XXXX" (white, 5x7 font) shows while
  `net_session_start()` brings the SoftAP, mDNS and HTTP server up, padded to 2 s → fade to black → the
  player restarts the current item (fade in) and the connection dot appears. No panel sleep, no offscreen
  rendering: the player task runs exactly as outside a session (frames, scenes, strips, boards,
  reader pacing, windows, queue entries).
- **Connection dot.** 6×6 px, corners clipped, brand accent `UI_ACCENT` (#C6A2FF), 8 px from the top and
  right edges (x 522–527, y 8–13). Steady while the hotspot waits for a client; pulsing (25 → 100 → 25 %
  of the accent colour, 16 steps of 100 ms = 1.6 s) while a station is associated (`WIFI_EVENT_AP_STA*`,
  `/status.session.clients`). It is a display overlay (`display_overlay_set()`): composited into the DMA
  bounce buffers of every flush that covers it, never written into the framebuffer, so `GET /screenshot`
  returns the content without it and no content path needs to know about it. The pulse costs one 6×6
  flush every 100 ms (the session holds the 160 MHz lock anyway). It can sit on top of the reader's pause
  mark box (both live in the top-right corner); the overlay wins.
- **Live API.** `/show`, `/next`, `/prev`, `/brightness`, `/reader`, `/queue/test`, `PUT /playlist`,
  `/time` act on the panel at once; `GET /screenshot` is the frame on the panel (minus the dot). Uploads,
  deletes and `PUT /playlist` restart the current item only when they concern it (see "Uploads during
  playback"). The short press works as outside a session.
- **Replacing what is on screen.** LittleFS refuses to rename over or unlink an open file, and an
  animation (and a reader item's text + index) is streamed from an open file. `PUT /assets/{id}`,
  `DELETE /assets/{id}`, `PUT /texts/{id}` and `DELETE /texts/{id}` therefore first call
  `player_release_files()`: if the item on screen streams from that id, the player closes the file and
  freezes on the frame it shows (button / scheduler commands that arrive meanwhile are replayed after it),
  the store replaces or deletes the file, and the reload that follows restarts the item. Safety net: the
  player unfreezes by itself after 30 s.

## Uploads during playback (2026-10-15)

**The incident.** An app sync while the `water` scene played: every stored atlas, the font and the
playlist PUT each sent the player a reload, and every reload restarted the item on screen: the scene was
re-initialised 9 times in 4 s (`player: scene water: arena 71564 B ... seed ...` every ~0.6 s, new seed each time,
plus a 250 ms fade each), which looked very laggy. None of those uploads concerned the scene.

**Now** (`player_reload_for(kind, id, deleted)`, `components/player/player.c` `reload()`): the playlist is
re-read on every change, but the item on screen restarts only when

- the uploaded / deleted id is what it uses: the asset of an animation, still or strip; a reader item's text, its
  font document or one of that font's atlases (the reader's font cache is dropped then too, so a replaced font
  is really reloaded);
- or `PUT /playlist` (or the playlist edit of a delete) changed or removed its own entry. Entries are compared
  by a hash of the whole JSON object (`pl_item_t.json_hash`: every key, also ones the firmware ignores; key
  order does not matter), so `scroll`, scene `params` / `seed`, `from` / `until`, `duration_ms`, ... all count.
  An identical entry at another index keeps playing; only the index is updated (`player: scene water: playlist
  entry moved from index 2 to 0 (keeps playing)`). Also a restart: a reader entry with `from_word` > 0 (the PUT
  is a seek request, PROTOCOL §5c) and a change of the lone-item status (its timing rules differ);
- or nothing runs (idle screen: the change may have made something playable), or the item's file had to be
  released for the change (`player_release_files()` above).

Scenes use no stored content, so uploads never restart them. A `/show` or queue entry keeps running unless its
own content changed. Every reload logs its decision:

```
I player: reload (upload asset font-688bc5cc-c): scene water keeps playing
I player: reload (playlist): scene water keeps playing
I player: restart scene water: reason=playlist entry changed or removed
I player: restart asset photo-e679: reason=upload photo-e679
I player: restart show strip e2e-strip: reason=delete e2e-strip (its file)
```

**Scene rate during uploads.** Live scenes drop to **15 fps** (from 30) only while an upload body is being
received and written (`PUT /assets`, `PUT /texts`: `player_upload_active()`, `player: scenes: upload in
progress, 15 fps cap` / `upload done, 30 fps again`). The rest of a session runs at full rate. (Before: 10 fps
for the whole session.)
- **Session end.** By the app (`/session/end`), the idle timeout or a weak battery: the dot disappears and
  the content just continues. By a long press: the "Done" card for 1 s, then the item restarts with a fade
  (the button deserves visible feedback).
- **`display_during_upload: false`** keeps the pass-3 behaviour (splash 3 s, panel asleep, offscreen
  render for `/screenshot`, everything visible after the "Done" card). The key is read when a session
  starts; changing it during a session affects the next one (`/status.session.display_on` reports the
  running session's mode).
- Power: a screen-on session costs the panel's usual current on top of the SoftAP (~100 mA); a panel-off
  session saves the panel's share. Sessions are short (default 120 s idle timeout).

## Always reachable (config `wifi_always_on`, default false)

- When true the SoftAP comes up right after boot (after the boot splash, with the "WiFi: PixelClip-XXXX" card)
  and stays up: no idle timeout, and `POST /session/end` answers `{"ok":true,"always_on":true,"message":...}`
  without ending anything (so the app's usual "sync, then end the session" flow does not switch it off).
  `/status.session.always_on` is true, the BLE status has `PIXELCLIP_BLE_FLAG_ALWAYS_ON`.
- Always-on sessions are always screen-on, whatever `display_during_upload` says (a permanent hotspot with
  a dark panel would leave the clip dark for good).
- What still ends it: a **long press** or BLE `wake` 0x02 (both also suspend always-on **until the next
  boot**: a later long press / BLE wake opens a normal, timed session), the battery dropping below 3.5 V
  (same suspension), deep sleep (hold / low battery). `PUT /config {"wifi_always_on":true}` lifts a
  suspension and makes the running session permanent at once; `false` gives it the normal idle timeout.
- **Battery cost.** A SoftAP cannot sleep: the radio idles at roughly **100 mA** (beacons every 102 ms,
  RX on), and the session holds the CPU at 160 MHz without light sleep. On the 500 mAh cell that is ~5 h
  for the hotspot alone, before the panel's own consumption — hours, not a night. Meant for bench work
  or while the clip is on USB.

## BLE doorbell (config `ble_wake`, default true)

The phone can open the hotspot without anyone pressing the button: the clip advertises over BLE all the
time (connectable, ~1 s interval), and writing one byte starts upload mode.

- **Contract** (`components/ble/include/pixelclip_ble_uuids.h`, copied by the app; `scripts/ble_wake.py` parses it):

  | | UUID | Properties | Value |
  |---|---|---|---|
  | service | `737B9B00-A500-43FC-B410-86AC8852E678` | primary, in the advertising packet | |
  | `wake` | `737B9B01-A500-43FC-B410-86AC8852E678` | write (with response) | 1 byte: `0x01` = start upload mode exactly like a long press (during a session: reset its idle timer); `0x02` = end the session (and suspend always-on until reboot) |
  | `status` | `737B9B02-A500-43FC-B410-86AC8852E678` | read, notify | 7 bytes LE: battery mV u16, pct u8, flags u8 (bit0 session_active = AP + HTTP up, bit1 usb_present, bit2 clock_ok, bit3 playing = panel on and an item (not idle) current, bit4 low_battery = a wake would be refused, bit5 always_on), current item kind u8 (0 none/idle, 1 asset/strip, 2 retired (never sent, not reused), 3 scene, 4 reader), protocol version u8 (1), last wake result u8 (0 none, 1 accepted, 2 refused: low battery, 3 refused: invalid). Readers must accept longer values. |
  | `info` | `737B9B03-A500-43FC-B410-86AC8852E678` | read | ASCII `"<device id>;<fw>"`, e.g. `"a1b2;0.1.0"` (device id = `/status device.id`) |
  | `req` | `737B9B04-A500-43FC-B410-86AC8852E678` | write without response (with response also accepted) | fast-lane request frames (see "BLE fast lane") |
  | `rsp` | `737B9B05-A500-43FC-B410-86AC8852E678` | notify | fast-lane response frames |

- **Advertising.** Name `PixelClip-XXXX` (same suffix as the SSID, also the GAP device name) in the scan
  response, flags + the 128-bit service UUID in the advertising packet (21 of 31 bytes). Legacy
  connectable undirected advertising, interval 1022.5–1285 ms (Apple's recommended values, so iOS
  background scans find it), TX 0 dBm. **Advertising continues while a central is connected** (2026-10-20),
  so a phone's scan always hears the clip: iOS sometimes keeps a link the app has let go, and a clip that went
  silent while connected looked "away" two metres from the phone. Up to two links (`CONFIG_BT_NIMBLE_MAX_CONNECTIONS=2`,
  controller activities 3 = advertising + two links, +828 B internal RAM); the **newest central wins**: when a second
  one connects, the first is dropped at once (its late writes are ignored; a fast-lane response in flight to it is
  not delivered). Advertising pauses only for the instant two links exist.
- **Idle drop.** A connected central that sends nothing for **20 s** (no read, write, subscription or MTU exchange;
  status notifications from the clip do not count) is disconnected by the clip, never while a fast-lane request is
  being handled (`ble: idle central dropped after 20 s`); checked every 5 s by an esp_timer that runs only while a
  central is connected. A client that keeps a link open on purpose (e.g. listening to `status`) must read or write
  something at least every 20 s, or reconnect when it needs the clip.
- **Why both, not one** (current): advertising while connected costs what advertising costs when disconnected
  (≈ 0.27 mA, below), only for as long as a link is up — seconds per request, at most 20 s for a forgotten one — so
  the average stays ≈ 1 mA. The idle drop alone would leave the clip invisible for up to 20 s after the app lets go
  (the failure seen in testing); advertising alone would let a forgotten link keep the radio busy for ever. A
  non-connectable advertisement while connected was rejected: the phone would hear the clip but could not connect
  to it when the held link is another phone's.
- **No pairing / bonding.** The hotspot is WPA2 with its own passphrase; the doorbell only opens it.
  Anyone nearby can ring it (= what a long press does) — that is the accepted trade-off.
- **Refusals.** While the battery is below the WiFi floor (3.5 V, no USB) a `0x01` write is answered with
  ATT error **0x80** (CoreBluetooth: `CBATTError` raw value 128) and `status` reports bit4 + last result 2.
  A value that is not exactly one byte → ATT 0x0D, any other byte → ATT 0x13 (last result 3). `0x02` is
  always accepted (ending a session only saves power).
- **Notifications.** On subscribe, right after every `wake` write, at session start/end, and whenever
  the packed value changed (checked every 2 s while subscribed).
- **App recipe (iOS).**
  1. `CBCentralManager.scanForPeripherals(withServices: [CBUUID(string: "737B9B00-A500-43FC-B410-86AC8852E678")])`
     (works in the background with the `bluetooth-central` mode; the UUID is in the primary packet).
  2. `connect`, `discoverServices([svc])`, `discoverCharacteristics([wake, status, info])`,
     `setNotifyValue(true, for: status)`.
  3. `writeValue(Data([0x01]), for: wake, type: .withResponse)`; an error with ATT code 0x80 = "charge the
     clip" (also visible in `status`).
  4. Wait for `status[3] & 0x01` (session_active; ~1–2 s), then join with
     `NEHotspotConfiguration(ssid: name, passphrase: pw, isWEP: false)` (join-once) and talk HTTP as usual.
  5. When done: `POST /session/end` (or write `0x02`), `cancelPeripheralConnection`.
- **Coexistence.** WiFi and BLE share the 2.4 GHz radio (ESP32-S3 software coexistence,
  `CONFIG_ESP_COEX_SW_COEXIST_ENABLE`): advertising continues during a session (so `0x02` works), at the
  price of a little WiFi airtime.
- **Light sleep.** `CONFIG_BT_CTRL_MODEM_SLEEP` (mode 1) lets the controller sleep between advertising
  events. The board has no 32 kHz crystal and the RTC slow clock is the internal 8 MHz/256 (kept for
  timekeeping), so the BLE low-power clock is the **main 40 MHz XTAL**, which then stays powered during
  light sleep (`CONFIG_BT_CTRL_MAIN_XTAL_PU_DURING_LIGHT_SLEEP`). Automatic light sleep keeps working
  between events. (`CONFIG_BT_NIMBLE_SLEEP_ENABLE` does not exist for the S3 controller in IDF 5.5; it is
  the C6/H2 equivalent.)
- **Expected current (not measured, logged at boot).** `ble: expected average current added by BLE: ~1.02 mA`
  from: XTAL kept on in light sleep ≈ +0.75 mA over the datasheet's 0.24 mA light-sleep floor; one
  advertising event (wake-up + ADV_IND on 37/38/39 at 0 dBm + the short scan/connect-request RX windows)
  ≈ 3.5 ms at ≈ 90 mA average (datasheet: BLE TX 0 dBm ≈ 100 mA, RX ≈ 80 mA, CPU active 25–40 mA), i.e.
  ≈ 0.32 mC per event / 1154 ms mean interval ≈ 0.27 mA. ≈ 1 mA ≈ 24 mAh a day ≈ 5 % of the 500 mAh cell.
  Verify with a meter on the battery lead (panel off/idle, USB unplugged); `ble_wake: false` removes it
  entirely (the stack is then never initialised).
- **Switching.** `PUT /config {"ble_wake":false}` stops and deinitialises NimBLE at once (radio off,
  memory back); `true` starts it again. `GET /ble` → `{"ok":true,"enabled","name","service_uuid","connected"}`.
- **Logs.** `ble: advertising PixelClip-XXXX (aa:bb:..) every 1022.5-1285.0 ms, service ...`, the current
  estimate, `central connected/disconnected`, `second central (handle 2): dropping the previous one (handle 1)`,
  `previous central disconnected`, `idle central dropped after 20 s (handle 1, silent 20 s)`,
  `wake write 0x01 (1 B) -> accepted`.

## BLE fast lane (PROTOCOL §3b)

Small requests go over the BLE connection the doorbell already uses, with no hotspot: the same endpoints,
the same handlers, the same status codes and JSON as HTTP. Bulk transfers stay on WiFi.

- **Characteristics** (in the doorbell service `737B9B00-…`, `pixelclip_ble_uuids.h`):
  `req` = `737B9B04-A500-43FC-B410-86AC8852E678` (write without response; writes with response are accepted
  too), `rsp` = `737B9B05-A500-43FC-B410-86AC8852E678` (notify). Subscribe to `rsp` before the first request
  (a response to an unsubscribed central is dropped and logged).
- **Framing** (both directions, `components/ble/pixelclip_frame.c`): a message is cut into frames of at most
  ATT_MTU−3 bytes; byte 0 of each frame is a header: bit7 = first, bit6 = last, bits 0–5 = sequence number
  (starts at 0, +1 per frame, mod 64); the rest is message bytes. One-frame message = both bits set.
  - request: `METHOD SP path LF [body]`, e.g. `POST /brightness\n{"value":200}` (`GET /status` with or
    without the LF; a CR before the LF is tolerated; path ≤ 255 bytes, query string allowed);
  - response: `STATUS SP LF [body]`, e.g. `200 \n{"ok":true}` (three-digit code, one space, LF; the body is
    exactly the HTTP response body).
- **MTU.** The clip's preferred ATT MTU is 517 (`CONFIG_BT_NIMBLE_ATT_PREFERRED_MTU`, also set in code) and
  it asks for 251-byte link-layer packets (data length extension) at connect. The central starts the MTU
  exchange (iOS / macOS always do; NimBLE's GATT client, which would let the clip start it, needs the
  central role and is compiled out): iOS typically ends at 185 (older) to 517, macOS similar. Frames are
  sized from the negotiated MTU (`ble: ATT MTU N` in the log).
- **Rules.**
  - One request in flight: a request whose first frame arrives before the previous response's last frame
    was sent is consumed and answered `429 \n{"ok":false,"error":"busy",…}` (after the running response).
  - Max 16 KB of body per request (`PIXELCLIP_BLE_API_MAX_BYTES`; the reassembly buffer adds room for the request
    line) → else `413 \n{"ok":false,"error":"too_large",…}`. The endpoints' own limits still apply (2 KB for
    the small JSON bodies, 16 KB playlist, as over HTTP).
  - A sequence gap, a continuation frame with no request open or an empty write → `400 \nbad_frame` (plain
    text) once; frames are then dropped until the next first frame. A new first frame while a request is
    still incomplete drops the incomplete one silently (the sender gave up on it).
  - A malformed request line → `400 \n{"ok":false,"error":"bad_request",…}`; unknown path → 404
    `not_found`, wrong method → 405 `method_not_allowed` (same lookup as `esp_http_server`).
  - **Allow-list:** everything except the WiFi-only routes (`api_route_t.wifi_only`): the bulk routes
    `PUT /assets/{id}`, `PUT /texts/{id}`, `POST /ota`, `GET /screenshot`, `GET /assets/{id}`, `GET /batlog`,
    `GET /coredump`, and the development routes `GET /imu`, `POST /imu/calibrate`, `POST /queue/test` (the
    link has no pairing: anyone in range could read the wearer's head motion or replace the calibration; the
    app calls them only after it has joined the hotspot). They answer
    `413 \n{"ok":false,"error":"use_wifi","message":…}` without running. So does a `PUT /config` that carries
    `ap_password` (nothing of the request is applied): the passphrase can only be set over WiFi. A response larger than 16 KB (e.g.
    `GET /assets` with many assets, `GET /texts/{id}` of a long text) is replaced by the same 413 `use_wifi`.
  - A fast-lane request never starts a WiFi session and never touches its idle timer (only HTTP requests
    do; `PUT /config {"upload_timeout_s"}` over BLE keeps the idle time already elapsed). It works with or
    without a WiFi session open; handlers are serialised across both transports (a BLE request waits up to
    10 s behind a running WiFi upload, then `503 busy`).
  - `PUT /config {"ble_wake":false}` over the fast lane is applied, but its response is lost: the radio is
    switched off by the request itself.
- **Inside the clip.** The NimBLE host task only reassembles (16.6 KB request buffer in PSRAM) and answers
  the protocol errors above; a complete request starts a short-lived worker task (10 KB internal stack,
  like the httpd task; nothing is held between requests) that runs the handler through `api_ble.c` into a
  16 KB PSRAM response buffer, then notifies it frame by frame with flow control: each frame waits until
  the NimBLE mbuf pool has room (24 + 24 PSRAM blocks; retries every 5 ms, gives up after 3 s without
  progress) and for its `BLE_GAP_EVENT_NOTIFY_TX`. Internal RAM: the 10 KB stack only while a request runs,
  ~1 KB static; `ble: central connected …, internal heap N B free (largest block M B)` is logged at every
  connection.
- **Log.** One line per request:
  `ble: fast lane: PUT /playlist -> 200, 2048 B in / 11 B out, 240 ms (rx 120, handler 60, tx 60; 1 frames, MTU 185)`
  (rx = first request frame to handler start, i.e. the upload; handler; tx = response notifications).
  Protocol errors log `fast lane: bad frame …`, `… -> 429`, `… -> 413`; handler errors also log the usual
  `http: ble PUT /playlist -> 422 Unprocessable Entity unknown_asset`.
- **Expected timings** (estimates from the link parameters, **not measured yet**; the log line above gives
  the real split). iOS uses a 15–30 ms connection interval and sends several write-without-response packets
  per connection event. `POST /brightness`, `/next`, `/show/...`, `/time`, `PUT /config`: 1 frame up, 1
  back → 1–3 connection events + a few ms of handler ≈ **30–100 ms**. `GET /status` (~700 B back: 4 frames
  at MTU 185, 2 at 512) ≈ **50–150 ms**. `PUT /playlist` of 2 KB at MTU 185 (12 frames up)
  ≈ 2–4 events up + validation and a LittleFS write (20–80 ms) ≈ **150–350 ms** — the PROTOCOL target is
  < 1 s. `GET /scenes` (~6 KB, 34 frames at 185) ≈ 200–400 ms. Scan + connect + discovery from a cold start
  adds ~1–3 s on the Mac (`ble_api.py` prints it separately); the app keeps the connection open.
- **From this Mac** (`scripts/ble_api.py`, needs `bleak`):

  ```sh
  scripts/ble_api.py GET /status
  scripts/ble_api.py GET /scenes
  scripts/ble_api.py POST /brightness '{"value":200}'
  scripts/ble_api.py POST /time "{\"epoch\":$(date +%s),\"tz_offset_s\":7200}"
  scripts/ble_api.py PUT /config '{"brightness":180}'
  scripts/ble_api.py PUT /playlist @playlist.json
  scripts/ble_api.py POST /reader '{"action":"pause"}'
  scripts/ble_api.py --repeat 20 GET /status          # timing
  scripts/ble_api.py GET /screenshot                  # -> 413 use_wifi
  ```
- **App recipe (iOS).** After `discoverCharacteristics([wake, status, info, req, rsp])`:
  `setNotifyValue(true, for: rsp)`; frame size = `peripheral.maximumWriteValueLength(for: .withoutResponse)`;
  write each frame with `.withoutResponse`, pacing on `canSendWriteWithoutResponse` /
  `peripheralIsReady(toSendWriteWithoutResponse:)`; reassemble `rsp` notifications (check the sequence,
  reset on a first frame); split at the first LF: status, body. Use the fast lane when no WiFi session is
  open and the route is not bulk; on `413 use_wifi` fall back to the doorbell + hotspot.

## Tonight scheduler (PROTOCOL §4 "Scheduling")

- **Windows.** Items may carry `"from"`/`"until"` (`"HH:MM"`, device local time = UTC + `tz_offset_s`).
  Active when `from <= t < until`; `from > until` crosses midnight (21:30–01:00 is active 21:30..00:59).
  A missing `from` means 00:00, a missing `until` 24:00 (`"24:00"` is accepted for `until` only).
  The rotation skips inactive items; if every item is inactive the idle screen shows, and the clip
  starts again by itself when a window opens. A 1 Hz tick (only when the document has windows or a
  queue, and only while the panel shows content) also ends the current item when its window closes.
  `POST /time` / `PUT /config {"tz_offset_s"}` re-apply the windows immediately, also during a session.
- **Queue.** `queue[]` entries (`id`, `at`, `type` asset|scene|reader|oracle|board with the playlist fields;
  the asset id is under `"asset"`) are sorted by `at`. The tick fires the earliest entry with
  `at <= now <= at + 600 s` while the clock is synced: fade to it for `duration_ms` (default 60 s),
  then the rotation resumes at the interrupted item. Entries found more than 600 s late are marked
  skipped. Fired and skipped ids are written to `/queue-done.json` (FIFO, 128 ids) at that moment, so
  they never fire again, across reboots too. `PUT /playlist` forgets the done-state of ids that are
  not in the new document (re-sending the same document does not re-arm anything; change the id to
  re-arm an entry). While a queue entry plays, the next due one waits for it to end (and is skipped if
  that makes it > 600 s late).
- **Precedence.** A queue entry replaces a running `/show`. A `/show` that arrives while a queue entry
  plays is deferred and plays right after it. `/next` / `/prev` / the button end a queue entry (and drop
  a deferred show) and return to the rotation.
- **Status.** `/status` has `"queue":{"pending","next_at","done","active"}` (`next_at` = `at` of the
  earliest pending entry or `null`; `active` = id on screen or `null`) and `"clock_ok"` (= `time.synced`).
- **Sessions.** In a screen-on upload session (the default) the player runs normally, so windows and the
  queue behave exactly as outside a session. In a panel-off session (`display_during_upload: false`) the
  tick is stopped: an entry that comes due then fires when the session ends if it is still within its 10 minutes.
- **`POST /queue/test {"id"}`** (non-normative, development only): plays that entry now exactly as when
  it fires, ignoring the clock and the done-state, without consuming it. 404 `unknown_entry` if the id
  is not in the stored queue. In a panel-off session it takes effect when the session ends (like `/show`).

## Clock and time anchor

There is no RTC chip or 32 kHz crystal. `components/timekeeping` keeps three states, reported in
`/status.time`:

| State | `synced` | `approximate` | `anchor_age_s` | Queue / windows |
|---|---|---|---|---|
| synced: `POST /time` since power-on / deep-sleep wake (software resets keep it), < 24 h ago | true | false | null | fire |
| approximate: rebuilt from the anchor at boot, or a sync older than 24 h | false | true | seconds since that anchor / sync | **never fire** (windowed items inactive) |
| unknown: no anchor was ever saved (fresh NVS) — the clock reads 1970 | false | false | null | never fire |

- **Anchor**: the wall clock (`anchor`, unix s) plus `tz` are written to NVS (`time` namespace) every
  60 s while the time is known (synced *or* approximate, so a chain of reboots never moves the clock
  backwards), at every upload-session end and on deep-sleep entry ("bye", battery floor). One 8-byte NVS
  entry per minute: a 4 KB page fills in ~2 h, negligible wear. The periodic save runs in the main
  (controller) task.
- **Boot**: without trust but with an anchor, the clock is kept if the RTC plausibly continued from the
  anchor (deep-sleep wake, software reset: it includes the time asleep); after a power-on it is set to
  `anchor + time since boot`, i.e. the clip is assumed to have been off for ~0 s. The boot log line
  `time: boot #N ... anchor A, clock NOT synced, approximate (...)` says which.
- `POST /time` clears `approximate` (synced again) and saves the anchor at once. `clock_ok`, the BLE
  `clock_ok` flag and the battery log's `epoch` keep following `synced` only.
- Strips, scenes and Reader pacing use `esp_timer` only (never the wall clock); the RTC time only feeds
  windows, the queue, the rows of a board (§5g: every row shows while the clock is not synced) and the
  battery log.

## Lone item (a one-item rotation plays indefinitely)

When the rotation has exactly one **active** item (after `from`/`until` filtering) it plays until
something changes (another window opens, a new playlist, `/next`, a show or queue entry):

- a still is held (no 5 s re-trigger, no re-fade); an animation loops seamlessly (frame N-1 → 0, no
  transition); a strip scrolls endlessly, ignoring `loops`; a scene runs on;
- `duration_ms` is ignored, **except for a reader item**: its cap (or the end of the text) ends the reading
  on the "fin" end card, which is then **held** (no restart; `loop: true` still loops). Restarts of the item
  (session end, `PUT /playlist` with the same item, a show ending) show the held end card again; `/next` /
  `/prev` (button double press), `POST /reader` seek or a `from_word` start the reading again. The held state
  is RAM only (a reboot starts the text from its saved progress, 0 after the end).
- when a `/show` (or queue entry) ends, the lone item is restarted with its own transition (fade by
  default: the show fades out, the item fades in once its first frame is in the framebuffer; an animation
  starts at frame 0, a strip enters again, a reader resumes at its saved word).

## Scrolling strips (PROTOCOL §4 "Scrolling strips")

- **Upload.** A `.hca` with flags bit1 `is_strip` must be exactly 1 frame, height 240, width 537–8192,
  raw or RLE16, and not also a glyph atlas; anything else → 422 `malformed`. The frame is validated by
  walking the RLE stream straight from the temp file (constant memory: an 8192-px strip would decode to
  3.9 MB, which may not be free while another strip plays). `GET /assets` reports `"strip":true|false`
  for every asset; the width is the usual `width`.
- **Items.** Playlist and queue asset items may carry `"scroll":{"px_per_s","direction","gap_px","loops"}`:
  `px_per_s` 10–400 (fractions allowed), `direction` `left|right`, `gap_px` integer 0–2000, `loops`
  integer ≥ 1 (≤ 65535). Every key is optional (defaults 80 px/s, left, 0, 1); a value out of range or of
  the wrong type, or a `scroll` that is not an object → 422 `invalid_playlist`. `scroll` only acts on
  strips (ignored for other assets); a playlist/queue strip without `scroll` plays as a still of its
  first 536 px (5 s default, like any still).
- **`POST /show/{id}` of a strip** always scrolls: the body may carry `"scroll"` (same keys, defaults and
  validation as items; a bad one → 422 `invalid_scroll`); without it the player borrows the `scroll` of the
  first playlist item, else queue entry, showing that asset (its `loops` dropped: a show lasts its duration,
  as PixelClipKit's `showScroll`), else uses the default 80 px/s, left, gap 0. Duration: `duration_ms` if given;
  else `loops` passes when the request's own scroll gives `loops`; else the /show default 60 s on an endless
  tape. The log says which scroll was used (`show <id>: strip scroll from ...`).
- **Playback.** On start the whole strip is decoded once into PSRAM (`width × 240 × 2` bytes, ≤ 3.9 MB).
  The allocation needs the strip plus 512 KB of headroom in the largest free PSRAM block; if that is short
  the cached scene arena and reader font are dropped (both rebuilt on demand) and it is retried, else
  the item is skipped with `strip <id>: needs N B of PSRAM ...` in the log. Each frame composes the 536-px
  window row by row (`memcpy` of at most three column segments, black for the gap) into the framebuffer and
  flushes it. The travel is computed from the elapsed time (`px_per_s × t`), never accumulated per frame,
  so the speed is exact whatever the frame jitter; frames are paced at 30 fps but only when the travel
  advanced by ≥ 1 px (10 px/s flushes 10 times a second). The strip enters from the off-screen side
  (from the right for `left`), copies repeat every `width + gap_px`, and the item ends when the last copy
  has left the screen: travel `536 + loops × width + (loops − 1) × gap_px` (same as the app's
  `StripScroller`). `duration_ms > 0` wins (copies repeat until it ends); a single rotation item scrolls
  forever (see "Lone item"); a queue entry without `duration_ms` plays the queue default 60 s. The decoded strip is freed
  when the item ends or the panel goes off (panel-off session); the offscreen render for `/screenshot` decodes just
  the visible 536 columns. CPU perf lock held while scrolling.
- **Logs.** `strip <id>: WxH RLE, decoded to PSRAM in N ms` at start, then every 5 s
  `strip: <id>: N fps at P px/s, compose X us, flush Y us`. Expected: compose ≈ 257 KB PSRAM read + write
  (~5–10 ms), flush ~14–16 ms → 30 fps. A raw 8192-px strip takes seconds to read from LittleFS at start
  (RLE text strips are typically 20–200 KB).

## Reader mode (PROTOCOL §5c)

RSVP speed reading: one word at a time, its optimal recognition point (ORP) drawn from the accent atlas and
pinned to column x = 230, the rest of the word white, a 2 px dim (`#52416B`) tick above and below the ORP
column. All layout, timing and painting is `core/include/rsvp.h` (the host tool `rsvp_preview` renders the
same frames, see core/README.md "Reader").

- **Texts.** `PUT /texts/{id}` (UTF-8, ≤ 1 MB, `X-Content-SHA256`): the body is written to a temp file,
  hashed and tokenised in the same streaming pass (`rsvp_tok_*`, constant memory), and the word index
  `/texts/<id>.idx` (128-byte header with word count, paragraphs, timing sum, SHA-256 and title, then one
  u32 LE per word: byte offset | flags << 29) is written next to it; both are renamed into place only when
  the hash matches and the text is valid. A word is re-read at play time from its offset with
  `rsvp_word_at()` (≤ 136 bytes per word, index entries read in blocks of 128), so a 1 MB text needs no RAM.
  `GET /texts` → `[{"id","bytes","words","title","progress_word","sha256","minutes"}]` (`minutes` at 300 wpm),
  `GET /texts/{id}` returns the raw text, `DELETE /texts/{id}` also drops the reader items using it and its
  progress. At most 64 texts.
- **Fonts.** `PUT /fonts/{id}` stores the font document after `rsvp_font_parse()` and a check that every
  named atlas is an uploaded glyph atlas of exactly `cell_w × cell_h` with at least one frame per glyph.
  The optional `"large"` face (§5f.11, same keys as `normal` / `compact`, for the Oracle's text screens; Reader
  ignores it) is checked the same way. `GET /fonts/{id}` returns it (+ `"ok":true`), `GET /fonts` lists
  `{"id","glyphs","cell_w","cell_h","compact","large"}`,
  `DELETE /fonts/{id}` also drops the reader items using it. At most 32 fonts. Deleting an atlas asset
  does not touch the fonts; a reader item whose font no longer loads is skipped.
- **Playback.** On start the font document and its 2–4 atlases are loaded whole into PSRAM (cached while
  the next reader item uses the same font; dropped when a strip needs the PSRAM) plus one glyph-decode
  scratch (`cell_w × cell_h` px, internal RAM if available). Each word: index entry + text bytes from
  LittleFS, `rsvp_paint()` (clears only the columns the previous word covered, band rows only), flush of
  that dirty rectangle. Pacing uses esp_timer timestamps (`next += rsvp_word_ms()`, never accumulated
  from late ticks); between words the player task blocks, so automatic light sleep runs (words are
  100–400 ms apart). The CPU perf lock is held only while a word is read, painted and flushed. A paragraph
  break adds a 300 ms blank (band cleared). After the last word the end card ("fin" in the accent atlas,
  "N words · M min" in white, M = whole-text time at the item's wpm) shows for 3 s; then the rotation
  moves on (`loop: true`: back to word 0). `duration_ms > 0` caps the session (paused time does not count).
  A queue entry without `duration_ms` reads for the queue default 60 s.
- **Progress.** `/reader-progress.json` (MRU, 64 texts) is written every 50 words, on pause, on seek,
  when the item stops (next item, window closed, session start) and as 0 after the end card; the next
  start resumes there. `from_word > 0` in a `PUT /playlist` document sets the text's progress once when the
  document is stored (later starts resume normally).
- **Controls.** `POST /reader {"action":"pause"|"resume"|"seek","word":n}` acts on the reader item on
  screen (also offscreen during a panel-off session) and answers with the `GET /reader` body; `GET /reader` →
  `{"ok":true,"active":true,"text","word","words","paused","wpm","font","title","end_card"}` (`word` = index
  of the word on screen, 0-based). Pause shows the font's `⏸` (U+23F8) glyph in the top-right corner, or a
  5×7 two-bar mark if the font has none; it survives a session or a reload of the same text, not
  `/next`. `/status.playlist.current` is `"reader:<text id>"`.
- **Logs.** `reader: font <id> loaded: WxH + compact, N glyphs, atlases B in PSRAM`, `reader: <id> "<title>",
  N words, from word K at W wpm`, then every 10 s `reader: <id>: word i/N at W wpm, n words in 10 s, paint X us,
  flush Y us`. Host timing (M1 Max) of layout + paint for 72×114 cells: ~17–20 µs per word; on the ESP32-S3
  expect a few hundred µs (glyph RLE decode from PSRAM) plus the band flush (~114 rows × ≤ 536 px ≈ 6–7 ms
  at 40 MHz QSPI).
- **Size.** Reader mode adds ~32 KB to the app: image 0x16e030 (1.43 MiB) of the 3 MB slot, 52 % free
  (clean `idf.py build`, 0 warnings).

## Oracle (PROTOCOL §5f)

A tarot oracle composed on the clip (PROTOCOL §5f, as amended by §5f.2 to §5f.12): the person holds a question,
presses (the deck is armed: "Shake the deck.") and shakes; the clip shuffles and turns **three cards** and reads them as the **lean draw** (§5f.7: at most 11 one-page
screens) — five short screens (by card, by position, by the numbers, together, and), then one detail screen per card
(its brief). There is no question card, no day mode and no card of the day since §5f.6; the number thread, the reading
pages and the paragraph screens are gone since §5f.7 (the paragraph is still composed for `/status`). The deck (cards
108×206, §5f.12) and the optional keyword atlas (160×34) the phone renders are pasted whole; every text is drawn on the clip from the reader bundle
with the reader font, in the largest face that fits (§5f.11, core `oracle_text.h`). State machine and screen layouts
in core `oracle.h`, texts in core `oracle_reader.h`.

- **Item** (playlist, queue, `/show` body): `{"type":"oracle","id":"<reader bundle: a /texts id>","deck":"<D>",
  "keys":"<K>","font":"<body font>","cards":22,"shake_g":0.9}` (`keys` optional, §5f.12: absent → no keyword row) plus optional `face_ms` / `page_ms` (default 0: paged
  by hand; a non-zero value still auto-advances) and `hold_ms` (the idle timeout back to waits, default 300 000; 0 =
  never). Queue entries name the bundle `"asset"`. `reader` (§5f.1) is accepted for one release and must equal `id`;
  `font_big` is accepted (no screen uses it since §5f.6); `notes` (§5f.7), `pages`, `mode` and `daily` (§5f.6) are
  accepted and ignored (not checked; deleting a notes asset does not touch the item).
- **Validation** (`PUT /playlist`, queue, `/show` body; `parse_oracle`, then `playlist_oracle_check` and the bundle
  check), in this order: `id` a valid id; `cards` integer 3–78; `deck` an asset id; `keys`, if present, an asset id;
  `shake_g` 0.4–2.0;
  `face_ms` / `page_ms` / `hold_ms` integers 0–86 400 000; `reader`, if present, = `id`; `font` required and
  `font_big` optional, valid ids — all of these → 422 `invalid_playlist`. Then: the bundle is a stored text (else 422
  `unknown_text`), the fonts are stored (`unknown_font`), the deck (and the keys, when given) exist (`unknown_asset`;
  `/show`: 404) and fit: **D** 108×206 (§5f.12), `1 + cards` frames; **K** 160×34 (§5f.12), `cards` frames; both **glyph
  atlases** (flag bit 0, `hcaenc --atlas`; a plain upload of such a size is refused with 422 `malformed`) → else
  `invalid_playlist` naming the asset. Last, the bundle
  (read and indexed, ≤ 96 KB) must have a `[prompt]` line and `card.<i>.reading` for every card `i < cards` → else
  `invalid_playlist` (`card.<i>.brief` is optional: a card without one has no detail screen). `/show` bodies:
  `invalid_item` for all but `unknown_asset`. A stored playlist whose bundle, fonts or deck vanished or changed
  skips the item. `DELETE /texts/{id}` removes the oracle items of that bundle, `DELETE /fonts/{id}` those whose body
  font it is, `DELETE /assets/{id}` those using it as their deck or keys.
- **Screens** (core `or_draw()`, §5f.10 – §5f.12; a TEXT op is a text screen drawn on black, the others are atlas
  pastes; cards 108×206): waits = the prompt + the back `D[0]` at y 17, x 8 (x 420 when the panel is flipped: the
  end away from the BOOT corner); armed = `[prompt.armed]` (else `[prompt]`) + the back, likewise; shuffle = 1.2 s at
  12 fps of random cards in the three slots, never a slot's previous card nor its chosen one, ending on A, B, C from
  1166.7 ms; three = `D[1+A|B|C]` at y 0, x 52 / 214 / 376 in both orientations (the shuffle's slots) + their
  keywords `K[A|B|C]` (160×34, each keyword's ink within the tile's 140 × 28 box at (10, 2)) at y 206, x 26 / 188 /
  350 when the item has keys (not during the shuffle; the tiles do not overlap and are pasted whole); lean = the

  `N of 22 cards have a detail (brief) screen, M of them beside the card`); hold = the three again.
- **Text screens** (`or_paint_text` → core `ot_draw_box`, the text layout's wrapping rules (core `textlay.h`, PROTOCOL §5c.1), static glyphs, the whole
  screen cleared first, the card pasted after): boxes of §5f.11 — beside a card (the prompts, a detail with its

  "and" lean screen's page test (`orr_fits` → core `ot_lean_fits`, §5f.7) is one page in the body font's **normal**
  face in the full-width box of the normal orientation (520 px × 224 rows), whatever face the screen
  is then drawn in — the
  phone applies the same rule, so both compose byte-identical text. The TEXT op's
  frame is decoded with `or_text_screen()` (waits prompt 0, armed prompt `0xD000`, detail `1 + card`, lean
  `0xE000 + screen`). A text screen repaints the whole frame with one full flush; a shuffle frame repaints only the
  card slots. Bundle, font (with its large and compact views), a layout (~13 KB) and a glyph scratch stay in PSRAM
  while the item shows; they are loaded at its start (the item does not start without them).
- **The arrow** (§5f.11, `or_paint_hint` → core `ot_draw_arrow`): one ▶ (8×9, the accent colour) in the corner where
  the BOOT button physically is — with the picture upright and the USB end on the right BOOT is the **top-right**
  button (the bottom-right one is the hardware reset): normally its right edge 8 px from the right edge, top row y 4,
  pointing right; flipped (`display_is_flipped()`) its left edge 8 px from the left edge, bottom row y 235, pointing
  left. On every screen but the shuffle (it always means "press to go on"); the 24×16 corner reserve around it
  (x 512…535 y 0…15, or x 0…23 y 224…239) holds nothing else. Painted last over a full repaint; a change of corner,
  or between the shuffle and the three, forces a full repaint, and `CMD_ORIENT` repaints the oracle when the panel
  flips while it shows (the arrow, the back / detail card and the boxes move live). The bundles' `[hint.*]` lines
  (§5f.9) are not drawn.
- **States and paging** (§5f.3, §5f.7, §5f.8, `/status.oracle.state`; core `or_turn` / `or_back`): one list —
  `waits` → (tap) `armed` → (shake or tap) `shuffle` → `three` → `lean` (screen 0 by card, 1 by position, 2 by the
  numbers, 3 together, 4 and) → `detail` A, B, C → `hold` (the three again). A **tap** (`POST /oracle/turn`) is the
  next screen (in `waits` it arms, in `armed` it deals, in `hold` it puts the cards back: `waits`); a **double tap**
  (`POST /oracle/back`) the previous one (`armed` → `waits`, `three` → `waits`; in `waits` it does nothing); taps and
  backs do nothing during the shuffle. A **shake** (metric ≥ `shake_g`, edge-triggered: ready again below
  `shake_g`/2) deals only on `armed`, where it wins over a tap in the same step; on `waits` and from the shuffle
  through `hold` it does nothing (§5f.8: no new draw mid-reading; the way to one is back to `waits`, tap, shake). The
  shake metric is polled (20 Hz) only on `armed`. `POST /oracle/draw` deals from any screen. Every draw is random: A, B, C distinct and never the previous draw's three as a set. Lean screens with no text and cards
  without a brief are skipped both ways. Nothing advances by itself unless `face_ms` (three) / `page_ms` (every lean
  and detail screen) are non-zero; `hold_ms` is the idle timeout: no tap, back or draw for that long returns any
  screen (`armed` included) to `waits` (an ignored shake does not count as input).
- **No interruptions while a draw is in progress** (§5f.8: the oracle current and not on `waits`, `armed` included;
  `or_holds()` / `or_hold_check()` in the player loop): the item's own end (`duration_ms`, also as a `/show` or a
  queue entry), queue entries and the time windows (closed / opened / a single item with
  company) wait: `next_deadline()` drops those deadlines and `service_timers()` skips them. When the oracle is back at
  `waits` (or replaced) they fire at once if still due: the item ends if its end has passed,
  and a scheduler tick runs at once (queue entries more than 10 minutes late are skipped as always). `/show`, a new
  playlist and `POST /queue/test` still act at once. With `hold_ms` 0 a draw left on screen holds
  them until someone taps back to `waits`. Logs: `oracle <id>: a draw (armed): the item's end, queue and
  windows wait` and `draw over (back at waits): item end due, scheduler tick now`.
- **The lean screens and the paragraph** (§5f.7, §5f.1 v3 composer, §5f.6: the closing is the centre card's): when a
  draw first reaches `three` the player composes the paragraph (`orr_compose`, ≤ 900 bytes, only for
  `/status.oracle.reading` outside the lean / detail screens) and the five lean screens (`orr_compose_lean`: one
  `[short.card]` variant for the row filled for A, B, C; a `[short.positions]` variant; the arc sentence with its
  numerals; the strongest finding other than the arc / `gaze.front` / `follow` / `echo`; the second such finding + " "
  + B's closing when that fits one page, else the finding alone if it fits, else the closing). "Fits one page" is the
  firmware's page test (`orr_fits`: `ot_paragraph_info` at full width with the body font = 1 page); the reference rule
  that the app mirrors is ≤ 150 code points, and with the bundles in `core/fixtures/tarot/` every lean screen of
  every row is under it. PSRAM arena from `orr_arena_bytes()`: 25 340 B for the 86 KB FR bundle. A new draw recomposes.
  `/status.oracle.reading` = the lean screen's text in `lean`, the card's brief in `detail`, the paragraph in `three` /
  `hold`, `""` in `waits` / `armed` / `shuffle`. Logs: `oracle <id>: N of 22 cards have a detail (brief) screen` at the start and
  per draw `oracle <id>: A B C: lean 11111 (…/…/…/…/… B), paragraph N B (couple.4-3,…,positions,closing), in T us`.
- **Button** (`app_main.c`, §5f.3): while an oracle shows (`player_oracle_showing()`: the current item, the panel
  on) a short press waits `ORACLE_DOUBLE_MS` (350 ms) for a second one: one tap → the
  next screen (`player_oracle_press()`), two → the previous one (`player_oracle_back()`); neither advances the
  playlist, on any screen (`armed` included: the check is the item, not the state). Outside an oracle a short press is "next item" at once (no delay); the reader's own single / double press
  (400 ms) is unchanged. Long presses unchanged; the bottom button is the hardware reset.
- **`POST /oracle/draw`** `{"cards":[a,b,c]}` (body optional; forces the row: three distinct integers 0…cards−1, else
  422 `invalid_cards`; other keys such as the old `card` / `question` are ignored), **`POST /oracle/turn`** (a tap: the
  next screen; arms in `waits`, deals in `armed`, nothing during a shuffle) and **`POST /oracle/back`** (extension, §5f.3: the previous
  screen, as a double tap; disarms in `armed`, nothing in `waits`). `/oracle/draw` deals from any screen (`waits` and
  `armed` included). All fast-lane eligible; answer
  `{"ok":true,` + the `/status.oracle` fields `}`; no oracle current or the panel off → 409
  `not_showing`.
- **`/status`**: `playlist.current` = `oracle:<bundle id>`; `"oracle":{"cards","state","cards_drawn":[A,B,C],"card",
  "page","reading"}` always present (cards 0, `waits`, −1s, `""` when none; §5f.6 dropped `mode`, `question` and
  `daily_card`). `state` is `waits|armed|shuffle|three|lean|detail|hold`; `cards_drawn` from `three` on; `card` = the detail
  screen's card, else −1; `page` = the lean screen 0–4 or the detail 0–2 (A, B, C), else −1; `reading` as above. BLE
  status kind: `ASSET`.
- **`/show`**: an oracle body shows it (path = the bundle); without a body, a bundle (a stored text) that a playlist (then
  queue) oracle item uses is shown as that oracle (a text no oracle item uses → 404 `unknown_asset`). `duration_ms` as
  for a still (5 s in a rotation, 60 s for `/show`
  and queue entries without one; the app sets it explicitly for Tonight), a lone item holds; a running shuffle
  finishes before the item ends (the lean screens do not hold the item).
- **Painting and memory**: the deck's header + frame table stay in PSRAM (≤ 79 × 12 B). **Deck cache**: at the
  item's first step (50 ms after it starts, before the clock of that step is read) the whole deck file — the cards'
  compressed frames, roughly 1 MB for 22 Dodal cards at 108×206 (§5f.12; an estimate from the card area) — is read into PSRAM (64 KB reads, yielding) and card frames are then
  decoded from memory (`hca_decode_frame`) straight into the framebuffer: a shuffle frame costs the decode and the slot
  flush only. Skipped (frames streamed as before, `deck … not cached` in the log) when the largest free PSRAM block is
  smaller than the file + 512 KB (so roughly 1.5 MB free in one block for a 22-card deck); released with the item. Keys
  frames are streamed from their file (`storage_frame_stream`, 4 KB buffer); no decoded frame is cached apart from
  the framebuffer. `or_draw_diff()`: with the same ground only the
  changed ops are repainted and flushed as their own rectangles (a shuffle frame = one 108×206 slot, or three);
  anything else is a full repaint + one full flush. Files are opened for a paint and closed after it, except during a
  shuffle (`player_release_files` closes them if an upload replaces one meanwhile).
- **Timing** (host M1 Max, `test_oracle` / scratch benches; measured at 104×198 — a 108×206 card is 1.08× the
  pixels): a real Dodal card scaled to 104×198 is ~41 KB RLE16 (the
  woodcut art barely compresses: raw is 41 184 B), decoded in 5–8 µs; a text frame (~7 KB) in ~11 µs. On the S3 the
  decode itself is ~1–2 ms; the cost is the LittleFS read (~1–2 MB/s: 20–40 ms for one card) plus the slot flush
  (~3 ms, 16 % of the 16 ms full flush). Expect **~25–45 ms per single-slot shuffle frame** (budget 83 ms: all 14
  frames) and **~70–130 ms per three-card frame** (3 reads): the three-card shuffle may show ~9–14 of its frames.
  Pacing is by time, so a slow frame is skipped, never stretched: both shuffles last 1.2 s and end on the chosen cards.
  A page turn (text frame + card + full flush) ~45–70 ms. After each shuffle: `oracle: <id>: shuffle done in T ms, N
  paints, paint X us avg / Y max, flush Z us avg`. With the deck cache (2026-10-18) the LittleFS reads are gone: a card
  is its decode (~1–2 ms on the S3) and a three-card frame ~5 ms of decode + three slot flushes (~10 ms), so both
  shuffles should show all 14 frames (to confirm on hardware from the log line above). Host (`test_oracle`
  `bench_frames`, M-series Mac, synthetic 15.6 KB card): three-card frame decode 60 µs streamed from a file in 4 KB reads
  vs 45–55 µs from memory — the host's page cache hides the flash cost, which is what the cache removes on the clip.
  Text screens (§5f.2) replace a 536×240 T frame streamed from flash (~7 KB RLE read + decode, then the full flush) by
  a layout + glyph paint: host `test_oracle_text` with the real readings: a reading page ~40 µs (≤ 4 lines, ~120
  glyphs), a face ~17 µs, a question ~37 µs, a page count ~13 µs per card (22 at the item's start). On the S3 (CPU
  ~30–60× slower than the host for this code, atlases in PSRAM) expect ~2–5 ms per text screen, against ~10–20 ms for
  the T frame it replaces; the full flush (~16 ms) is unchanged, and shuffle frames do not redraw the text. At the
  item's end the log says `N text screens drawn (faces: L large, N normal, C compact, K cut), X us avg / Y max`; the
  face choice (§5f.11) lays a screen out up to three times (large, normal, compact), so expect up to ~3× the layout.
- **Holds**: the IMU (50 Hz) while visible (released with the panel off); the `ORACLE` perf owner
  only during a shuffle; on `armed` the shake metric is polled every 50 ms (light sleep in between); on the other
  screens no polling at all, only the state's own timers (§5f.8: a shake counts only on `armed`). The player's between-iterations check covers the new owner.
- **Logs**: at start `oracle: font … loaded: WxH + compact + large, …`, `oracle <id>: 22 cards, deck …, font …
  (large / normal / compact), shake 0.90 g, imu yes, waits painted in T ms`, then `deck … cached in PSRAM: N B, 23
  frames, in T ms` and `N of 22 cards have a detail (brief) screen, M of them beside the card` (the start line names
  `keys …` or `keys (none)`); per draw
  `oracle <id>: draw (shake|tap|POST /oracle/draw[, forced]): A B C` and the lean line above.

## Live scenes

- Playlist and queue items `{"type":"scene","scene":"sand","params":{...},"seed":42}`. `PUT /playlist` checks the
  id and params against the core registry (`GET /scenes` is `scene_describe_json()` verbatim, with `name`
  and `defaults`): unknown id → 422 `unknown_scene`; `params` not a flat object, an enum value not in its
  list, an integer out of range, or a boolean for an enum → 422 `invalid_params`; booleans map to 1/0;
  unknown keys are ignored, missing keys take the defaults. Firmware default override: `fire` gets
  `smooth=1` unless the item sets `smooth` (the registry, and so `GET /scenes`, says 1 too today).
- `seed` (optional, integer 0–4294967295, else 422 `invalid_playlist`) makes the scene deterministic apart
  from its motion input (also across session ends); without it every start uses `esp_random()`.
- The arena (`scene_arena_bytes()`, worst case over all params, < 140 KB) is allocated once in PSRAM
  and reused. Each frame: `scene_step()` with the IMU gravity (dt clamped to 50 ms), `scene_render()`
  into the framebuffer, flush of the dirty rectangle. Pacing targets 30 fps (33 ms, at least 2 ms of
  blocking between frames so the idle task / watchdog run). While a scene is on screen the CPU perf
  lock (160 MHz) and IMU sampling are held; both are released when it ends or the panel goes off.
- Every 5 s the log prints `scene: <id>: N fps, step X us, render Y us, flush Z us`. Expect the flush to
  dominate: grid scenes (sand/water/snow/fire/lava) repaint the whole 536×240 area every frame, so a
  frame costs one full-frame flush (~14–16 ms at 40 MHz QSPI) plus step+render (a few ms; ~0.1 ms on
  a desktop CPU). `balls` only flushes the moving regions. If a grid scene logs < 25 fps, try
  `scale` ≥ 4 (the default) or 80 MHz QSPI in menuconfig.
- `duration_ms: 0` = 60 s (single-item playlists play forever). `playlist.current` is `"scene:<id>"`.
  Offscreen (panel-off session) the scene is simulated for ~1.3 s so `/screenshot` shows something.
  After a panel-off session the scene restarts (from a new seed unless the item has `seed`). Whenever something
  else painted the framebuffer or the panel faded (system screens, fades, output toggles) the player calls
  `scene_invalidate()` before the next render, so the dirty-rect flush never relies on stale pixels.
- Gravity comes from the IMU (`imu_get_gravity()`, display frame, PROTOCOL §5b: the direction things
  fall). Without an IMU (not found, or disabled in menuconfig) scenes get a fixed (0, 1, 0) = upright.
- **Words** (PROTOCOL §5b.1, core `scene_words.c`): `{"type":"scene","scene":"words","id":"<sheet>","params":
  {"bounce":60}}` — the app renders each word of the text as one frame of a **sheet** asset (an .hca of 1–12 frames,
  same w × h, w ≤ 536, h ≤ 240, N·w·h ≤ 514 560 px, black = transparent) and the clip bounces the words with the
  movement. Upload: a sheet that is not 536 × 240 must carry the glyph-atlas flag (flags bit 0, `hcaenc --atlas`),
  as storage accepts no other non-full-screen still. `id` names the sheet in `items[]` and `/show` bodies; in `queue[]` entries it is `"asset"` (their `id` is
  the entry's). Validation (`parse_words_sheet`): `id` missing / not an id → 422 `invalid_playlist`; no such asset →
  422 `unknown_asset` (`/show` body: 404); a strip, 0 or > 12 frames, w > 536, h > 240 or N·w·h > 514 560 → 422
  `invalid_playlist` (`/show`: `invalid_item`); `bounce` 0–100 (else `invalid_params`). A stored playlist whose sheet
  vanished or no longer fits skips the item; `DELETE /assets/{sheet}` drops the words items and queue entries using
  it. `POST /show/{sheet}` with a scene body shows it; without a body a sheet used by a playlist (then queue) words
  item is shown as that item (like the oracle's bundle). `playlist.current` = `scene:words`.
- **Words at start** (`words_load`): the whole sheet file is read into PSRAM, every frame decoded into one PSRAM
  buffer (N·w·h·2 B, ≤ 1 MB) and handed to the scene (`scene_words_set_sprites`), then the file buffer is freed; the
  sprites stay until the item ends. Needs the sprites + 512 KB in the largest free PSRAM block, else the item does not
  start. Log: `scene words: sheet <id>: 3 frames 200x60, 3 words, sprites 72000 B in PSRAM, decoded in T ms (largest
  block now X B)` (`(every frame is black: a black screen)` when no frame has ink). Rendering flushes only the moved
  words' rectangles (nothing at rest).

## Board (PROTOCOL §5g)

A list of timed row pictures that scrolls (a timetable, the rest of today's agenda): the sender draws the rows into a
sheet and pushes a `board` item (the iOS app has no screen that builds one yet); the clip stacks them, drops each row by its own clock once its time has passed, and
scrolls when the list is taller than the screen. Composition in core `board.h`.

- **Item** (`items[]`, `POST /show` bodies; `queue[]` names the sheet `"asset"`): `{"type":"board","id":"<sheet>",
  "header":0,"empty":1,"rows":[{"frame":2,"until":1761062400},…],"scroll_px_s":16,"duration_ms":60000}`.
  **Validation** (`parse_board`; 422 `invalid_playlist` unless noted, `/show` bodies `invalid_item` / 404): the sheet
  id missing or invalid; the sheet absent → `unknown_asset` (a stored playlist skips the item); a strip, 0 or > 48
  frames, w > 536, h < 16 or > 240, N·w·h > 1 048 576 px; `header` / `empty` (optional) not a frame 0…N−1;
  `scroll_px_s` not an integer 4…60 (default 16); `rows` not 1…47 objects; a row's `frame` not 0…N−1; its `until`
  (optional) not an integer 0…4 294 967 295 (unix seconds). A sheet that is not 536 × 240 must carry the atlas flag
  (storage rule). `DELETE /assets/{sheet}` drops the boards and queue entries using it; `POST /show/{sheet}` without a
  body shows the playlist (then queue) board using it. `playlist.current` = `board:<sheet>`; `duration_ms` 0 = 60 s
  (a lone item holds).
- **At start** (`board_begin`): the whole sheet is read into PSRAM, every frame decoded into one PSRAM buffer
  (N·w·h·2 B, ≤ 2 MB; needs that + 512 KB in the largest free block, else the item does not start), the core board set
  up with the clock (`timekeeping_now()`, `timekeeping_synced()`: every row while the clock is not synced) and the
  first screen rendered. Log: `board: sheet <id>: N frames WxH, B B in PSRAM, decoded in T ms (largest block now X
  B); R of M rows (clock synced), scrolling at 16 px/s`.
- **Running**: once a second (`board_tick`) the row set is re-evaluated (a static board repaints at once; a scrolling
  one takes the new set at its next loop boundary); while it scrolls, `board_frame` steps it at ≤ 30 fps and flushes
  only the rows' column below the header (nothing while static: no wake-ups but the 1 Hz tick). After something else
  painted (a fade, a system screen) the next render is a full one. The board flips with the panel like a picture. Logs: `board
  <id>: R of M rows now` / `… at the loop boundary (static now)`, every 30 s while scrolling `board <id>: N frames
  in 30 s, render X us, flush Y us (avg)`.

## Orientation (PROTOCOL §4 "Orientation", 2026-10-16)

The clip is worn on either side of the head, so the whole screen can turn 180°. Config `orientation`:
`auto` (default) | `normal` | `flipped`, persisted in `/config.json`, applied at once by `PUT /config` (WiFi or BLE
fast lane: same handler). `/status` reports `"orientation":{"mode":"auto","flipped":false}`, `GET /imu` adds
`"flipped"`.

- **The flip is the panel's.** `display_set_flipped()` writes MADCTL (0x36) `0xF0` → `0x30` (MX and MY toggled:
  bit 7 MY, 6 MX, 5 MV, 4 ML) under the display lock, then re-sends the framebuffer once (MX/MY act on the
  write addressing, so GRAM only turns over when rewritten). No per-frame cost, no framebuffer transform: assets,
  strips, scenes, reader, oracle, boards, system screens and the overlay dot all flip; `/screenshot` stays upright.
  With the panel asleep the register is written at the next `display_on()`.
- **Window offset: 0 in both orientations** (`FLIP_GAP_X/Y` in `display.c`, applied with `esp_lcd_panel_set_gap`):
  the RM67162 GRAM is exactly the 240×536 glass, so mirroring maps 0..535 onto 535..0 and nothing shifts (the
  Waveshare demo and LilyGo's driver for the same 1.91" panel use no offset in any rotation).
- **Detector** (`components/player/orient.c`), mode `auto`: runs as the IMU task's per-sample hook (no extra
  task, ~50 B of RAM): 10 Hz background sampling, 50 Hz while a scene holds the IMU. Low-passed display-frame gravity
  `gy < −0.5` for 1 s continuously → flipped, `gy > +0.5` for 1 s → normal, in between (flat on a table, on its
  side) → unchanged. A gap of > 0.5 s in the samples restarts the second. The decision goes to the player task as a
  queue command, so the flip lands between two frames. At boot it takes a ~0.1 s reading before the splash and
  starts flipped if gravity already says so. Log: one line per change, `orientation: flipped (gy=-0.83)` /
  `orientation: normal (gy=0.97)` (forced: `orientation: flipped (forced)`), nothing while stable.
- **Live scenes are exempt** (2026-10-16): they already answer to real gravity, so while a scene
  shows the panel is upright and the scene gets the true vector; the decided orientation returns with the next
  item (`orient_sync()` in `player.c`, run on every item start and on each detector decision). **Except `words`**
  (§5b.1, `scene_follows_orientation()`): text must read upright, so it flips with the panel like a picture, and
  `scene_gravity()` hands it the vector in the flipped display frame (gx, gy negated, `scene_gravity_flipped()`) —
  from its very first sample, taken before the panel turns — so the words still fall to the physical bottom.
- Depends on the IMU axis map being right (README "IMU bench check"): with a wrong Y sign, `auto` would show the
  picture upside down when the clip is upright. Without an IMU, `auto` stays normal.

**Hardware check (one flash).** `curl -s -X PUT $CLIP/config -H 'Content-Type: application/json' -d '{"orientation":"flipped"}'`: the picture must
turn over at once and sit exactly where it was, edge to edge (no stale band on one edge, nothing cut off on the
other; a still with a 1-px frame or text in the corners shows it best). If it is shifted by N px, set `FLIP_GAP_X`
(long edge) / `FLIP_GAP_Y` (short edge) in `components/display/display.c` to N (even). Then `"auto"` and turn the
clip upside down: it flips after ~1 s (`orientation: flipped (gy=-0.9x)` in the log), and back when turned upright.

## IMU bench check (QMI8658C)

Boot log: `imu: QMI8658C at 0x6B (rev 0x..)` (0x6A is probed second). Sampling runs at 10 Hz in the
background while `orientation` is `auto`, else is off, until a scene runs or `GET /imu` is called (then 30 s at
50 Hz). `GET /imu` also reports `"flipped"` (the vectors are never rotated). The response is
`{"ok":true,"present":true,"g":[gx,gy,gz],"shake":s,"samples":n,"g_lp":[...],"raw":[...],"calibrated":bool,"axis_map":[[..],[..],[..]],"addr":"0x6B"}`;
`g` is gravity in g in the display frame (+x right, +y down, +z out of the glass), `raw` the chip
reading (+1 g on the axis pointing up), `axis_map` the matrix in use (`g[i] = Σ axis_map[i][j]·raw[j]`)
and `calibrated` whether it comes from a stored bench calibration.

**Calibration (no rebuild).** With the clip on the bench and a session open:

1. Hold it upright (landscape, image readable, vertical) and still:
   `curl -s -X POST $CLIP/imu/calibrate -H 'Content-Type: application/json' -d '{"step":"upright"}'` → `{"ok":true,"step":"upright","raw":[...],"next":"faceup",...}`.
2. Lay it face up (glass toward the ceiling) and still:
   `curl -s -X POST $CLIP/imu/calibrate -H 'Content-Type: application/json' -d '{"step":"faceup"}'` → `"calibrated":true,"axis_map":[...]`.

Each step averages ~0.5 s of samples (25 at 50 Hz). Errors: `422 not_still` (an axis spread > 0.1 g:
hold it still), `422 ambiguous_pose` (|reading| not 0.8–1.2 g or no single axis above 0.7 g: square it
up), `422 calibration_failed` after the second pose if both readings are on the same chip axis (both
captures are discarded: redo both), `409 no_imu`, `422 invalid_step`. The steps can come in either order;
once both are captured `scene_axis_map_calibrate()` derives the signed permutation, which is applied at
once and stored in NVS (namespace `imu`, key `axis_map`, loaded at boot: `imu: axis map from bench
calibration: [...]`). `{"step":"reset"}` erases it. Then run the checks below; `scripts/e2e.sh` with
`E2E_CALIB=1` walks through the same two steps with prompts. Paste the printed matrix into
`SCENE_IMU_AXIS_MAP` (core) / `IMU_AXIS_MAP` (imu.c) later if it should become the compiled default.

Checks:

1. Clip upright (display landscape, text readable): `g ≈ [0, 1, 0]`.
2. Lying face up (glass toward the ceiling): `g ≈ [0, 0, -1]`.
3. Upright, right edge tilted down: `g[0] > 0`.
4. Shake it: `shake` jumps above ~0.5, then decays to ~0 within a second.

Fallback without a stored calibration (also fixes wrong signs/axes without code changes) in
`idf.py menuconfig` → PixelClip IMU:
`PIXELCLIP_IMU_SWAP_XY` if step 1 shows ±1 in `g[0]` instead of `g[1]` (apply first), then
`PIXELCLIP_IMU_FLIP_Y` if step 1 reads −1, `PIXELCLIP_IMU_FLIP_Z` if step 2 reads +1, `PIXELCLIP_IMU_FLIP_X` if
step 3 is negative. Rebuild, flash, repeat. The default assumption (identity map: chip on the back of
the board, chip +Y toward the top of the image) is explained at `IMU_AXIS_MAP` in
`components/imu/imu.c`. A stored calibration overrides both the compiled map and the flips. INT1/INT2 (GPIO45/46, strapping pins) are never enabled or touched.

## Boot splash

If `firmware/main/assets/splash.hca` exists when CMake configures (`idf.py reconfigure` after adding
it), it is embedded (`EMBED_FILES`) and played once at boot before the playlist: fade in to the
configured brightness, at most 3 s, fade out. It must be a 536×240 non-atlas `.hca` of at most 300 KB

## Battery logger

There is no power meter, so the firmware logs its own discharge curve. Every 60 s it appends
`epoch,uptime_s,mv,pct,usb,mode,display,brightness` to a two-file ring (`/batlog.csv` +
`/batlog.1.csv`, each ≤ 32 KB, so ≤ ~64 KB total, roughly 20 h of history).

- `epoch` is 0 while the clock is not synced; `uptime_s` always counts.
- `usb` is the heuristic USB-present flag (see below), `mode` is `playing | idle | upload`,
  `display` is `on | off`, `brightness` is the perceptual 0–255 level.
- `GET /batlog` returns `text/csv` with a header line, oldest first. `DELETE /batlog` clears it.

To measure runtime: charge, `DELETE /batlog`, end the session, wear it until it dies, then reconnect
and `GET /batlog`.

## Power behaviour

- CPU: esp_pm DFS 80 ↔ 160 MHz with automatic light sleep. 160 MHz is held (pm lock) only while
  decoding/flushing a frame, while a live scene is on screen, and for the whole upload session
  (permanently with `wifi_always_on`, see its battery cost).
- BLE doorbell: advertising every ~1.15 s with the controller in modem sleep between events; the main
  XTAL stays powered in light sleep as its clock. Estimated +1 mA average (not measured; see "BLE
  doorbell"). `ble_wake: false` removes it.
- IMU: accelerometer only, gyro off. 50 Hz while a scene is visible or `GET /imu` ran in the last 30 s; 10 Hz
  (one I2C read every 100 ms, a short wake from light sleep each) while `orientation` is `auto` (the default) for
  the flip detector; otherwise the sensor is disabled (CTRL7 = 0) and its task blocked (no wake-ups):
  `orientation` `normal` / `flipped` removes the 10 Hz cost.
- Scheduler: the 1 Hz tick only exists when the playlist has windows or a queue. Still images between ticks let
  the chip light-sleep; the panel keeps the image in its own GRAM.
- While USB is present (host SOF or the VBUS proxy) and 5 s after, the chip does not auto-light-sleep (power.c's
  USB hold, "USB light-sleep inhibit"; keeps the console alive) — except in the bench soak build. The CPU stays powered in light sleep (`CONFIG_PM_POWER_DOWN_CPU_IN_LIGHT_SLEEP=n`).
- RTC watchdog (40 s, counts in light sleep, fed every 5 s while the player is alive) and the other battery
  hang measures: "Light sleep on battery".
- RTC slow clock: internal 8 MHz/256 (no 32 kHz crystal on the board), more stable than the
  136 kHz RC; system time is tracked by it during light sleep.
- Battery: GPIO1, 100k/100k divider, curve-fitting calibrated, 30 s sampling, 4-sample average,
  LiPo table in `power.c` with 0 % = 3.40 V (the firmware cutoff from HARDWARE.md §8). Low battery
  = `pct ≤ low_battery_pct` (default 8 % ≈ 3.66 V) on two consecutive samples or < 3.40 V: "Battery
  low" banner for 10 s, then deep sleep. No checks while USB is present, and none until the ADC has
  produced a plausible reading (a broken ADC never puts the clip to sleep). WiFi sessions are refused
  / ended below 3.5 V; during a session every low reading only ends the session (never deep sleep), and the
  average restarts from rested readings afterwards. USB presence is re-evaluated every second.
- Light sleep isolates GPIOs (`CONFIG_PM_SLP_DISABLE_GPIO`); the display bus pins (CS, CLK, D0-D3,
  RST) are excluded with `gpio_sleep_sel_dis()` so the panel never sees a floating bus while it
  holds the image.

## Light sleep on battery

**Decision (2026-10-17): no automatic light sleep while the panel is on.** The app holds `POWER_AWAKE_PANEL` from
`display_on()` to `display_off()` (display power hook, `panel_power_changed()` in app_main.c). Evidence: on battery
the clip napped ~160 times a second (9 132 naps in 58 s) and, within minutes to hours, the picture froze while the
chip stayed alive (the battery log kept writing through a 3 h 45 min run with several freezes; an 8-ball answer
stayed on screen; a "bye" screen stayed lit after a power-off because the panel-off command never took). A build
with light sleep off ran scenes, the 8-ball and power-off/on on battery with no fault. The naps corrupt the panel's
command interface (QSPI bus parked and re-driven around every nap; CS/CLK pins are kept out of the GPIO isolation,
but something still gets through at that rate), so the panel keeps refreshing its GRAM and ignores further commands.
Since the panel is on whenever the clip is in use and dominates the budget, light sleep bought little; it remains
enabled and is used whenever the panel is off (panel-off upload sessions, the low-battery banner path, the
boot-loop guard). Deep sleep (power-off) clears every wake source first (auto light sleep leaves an RTC timer trigger
armed; a powered-off clip woke itself at once). The power-off choreography holds `POWER_AWAKE_POWEROFF` and keeps the
RTC watchdog armed until `power_deep_sleep()`.

**The incident (2026-10-13, on battery).** The clip played and answered Bluetooth; a WiFi send of a new
animation went through; after the session ended the panel kept one frame of that animation, the player
stopped, BLE was gone ("can't find clip"), and plugging USB showed no USB device at all. RESET recovered it
(battery 98 % at rest; it had read 69 % under WiFi TX). Reading: the chip went into automatic light sleep after
the session and never came back. It cannot happen on USB: `CONFIG_USJ_NO_AUTO_LS_ON_CONNECTION` keeps a
USB-connected chip out of light sleep. (That turned out not to hold: since 2026-10-15 power.c's USB hold does it, see
"USB light-sleep inhibit".)

**What the code audit found** (IDF v5.5 sources quoted by file):

1. *Nothing could recover a chip that sleeps and never wakes.* The task watchdog runs on the timer-group
   watchdogs, which the light-sleep code stops while asleep (`esp_hw_support/sleep_modes.c` `suspend_timers`,
   `SOC_SLEEP_TGWDT_STOP_WORKAROUND`), and `CONFIG_ESP_TASK_WDT_PANIC` is off (it only prints). IDF's own
   light-sleep safety net (the 1 s RTC watchdog armed in `esp_light_sleep_start`) is created through
   `wdt_hal_init()`, which sets the RWDT's *pause in sleep* bit (`hal/wdt_hal_iram.c`): it catches a failed
   wake-up, not a sleep that never ends. **Fix: our own RTC watchdog that keeps counting in light sleep** (below).
2. *Every wake source but the button hangs off the RTC timer.* Player frames, the power task, the controller
   are FreeRTOS timeouts that tickless idle turns into `esp_sleep_enable_timer_wakeup(min(next tick, next
   esp_timer))` (`esp_pm/pm_impl.c` `vApplicationSleep`), and the S3 BLE controller wakes the chip for its
   advertising events through an esp_timer of its own (`bt/controller/esp32c3/bt.c`, "btSlp"). One broken
   wake path therefore kills the player, BLE and the USB console *together* — exactly what was seen. (Next
   time, before RESET: a short BOOT press wakes it through the GPIO0 level wake-up. If the clip resumes, it
   was asleep with a dead timer wake; if not, it was a hard hang.)
3. *The transition right before the hang was `esp_wifi_deinit()` with NimBLE and software coexistence
   active* (every session end). The deinit tears down the coexistence arbiter that the BLE controller keeps
   using, unregisters the WiFi sleep/wake hooks (`esp_sleep_disable_wifi_wakeup`, the skip-light-sleep
   callback, MAC/BB power-down callbacks) and drops the WiFi/BT power-domain and PHY references
   (`esp_wifi/src/wifi_init.c` `wifi_deinit_internal`); the coexistence and PHY parts are closed source. The clip
   ran fine on battery before the session and died on the first light sleeps after it. **Fix:** the driver
   stays initialised while BLE runs; a session end is `esp_wifi_stop()` + `esp_wifi_set_mode(WIFI_MODE_NULL)`
   (radio off, PHY released, the driver's own PM lock released). The driver is deinitialised only when BLE is
   off (at session end, or right after `PUT /config {"ble_wake":false}` outside a session). An AP has no
   power save, so `esp_wifi_set_ps` has nothing to restore; nothing else of coexistence is configured.
4. *CPU power-down in light sleep* is the IDF 5.5 default for the S3 (`CONFIG_PM_POWER_DOWN_CPU_IN_LIGHT_SLEEP`:
   the CPU is powered off and its context restored from an 8.6 KB retention buffer at every wake-up). With a
   hang that looks like "never came out of sleep", that path goes: **disabled in `sdkconfig.defaults`** (costs
   ~0.65 mA while asleep, a few % next to the panel; gives back 8.6 KB of internal RAM). The bench build can
   turn it back on to bisect.
5. *PM locks.* Every acquire has its release on every path (`net_session_start` failure → `net_session_stop`
   releases; the player's short holds are begin/end pairs with no early return in between; scene / strip holds
   are flag-guarded). A leak would have the opposite symptom (no sleep, a drained cell), not a hang. Now
   accounted per owner (`power_perf_acquire/release(owner)`): the player checks between loop iterations that it
   holds no transient lock and that the scene / strip holds match the screen; after every session the controller
   logs `app: after session: perf holds transient=0 scene=0 strip=0 session=0 oracle=0; esp_pm locks held: none` (the
   esp_pm lock table, minus the running core's `rtos` lock) and flags `PM LOCK ACCOUNTING` if the session hold
   is not back to zero (fatal in the bench build).
6. *Display / QSPI.* The SPI master holds an APB_FREQ_MAX lock from queueing a transaction until its completion
   interrupt (`esp_driver_spi/src/gpspi/spi_master.c`), so light sleep cannot start during a DMA flush; our
   flush waits are bounded (500 ms per band). esp_lcd's `tx_param` does wait forever for queued colour
   transfers — a lost interrupt would freeze the player only, which the liveness rule now turns into a reboot.
7. *Pacing.* The player paces with queue timeouts (honoured by tickless idle), never esp_timer callbacks; it now
   never blocks longer than 5 s (`HEALTH_PLAYER_MAX_WAIT_MS`, it beats every pass). Our one-shot esp_timers
   (session idle / end, double press) always wake the chip (`skip_unhandled_events` exists only for periodic
   timers; spelled out in `net.c`).
8. *GPIO isolation.* `CONFIG_PM_SLP_DISABLE_GPIO` isolates every pad in sleep from a startup hook
   (`esp_hw_support/sleep_gpio.c`), before `display_init` / `imu_init` exclude their pins with
   `gpio_sleep_sel_dis`; nothing in the WiFi path re-enables it. Re-applied after every session anyway
   (`display_sleep_pins_apply()`, `imu_sleep_pins_apply()`, idempotent).
9. *BLE modem sleep.* The main XTAL is the BLE low-power clock and is kept powered in light sleep
   (`CONFIG_BT_CTRL_MAIN_XTAL_PU_DURING_LIGHT_SLEEP` → `esp_sleep_pd_config(ESP_PD_DOMAIN_XTAL, ON)`, refcounted);
   without that option the controller would create a `btLS` no-light-sleep lock instead. Correct as configured.
10. *USB-Serial-JTAG.* No driver is installed: the console's no-driver path waits at most 50 ms once for a host
    and then drops output (`esp_driver_usb_serial_jtag/src/usb_serial_jtag_vfs.c`), so logging never blocks
    without a host. On battery the log level drops to WARN (less work between sleeps); USB brings INFO back.
    Nothing else uses the USJ. Note that "no USB device after plugging in" does not prove the chip *never*
    woke: the no-light-sleep lock is only taken by a tick hook that must already see SOF packets, so a chip
    that wakes for milliseconds at a time can miss enumeration. (Since 2026-10-15 the IDF lock is off and power.c's
    USB hold replaces it; the same limit applies to a plug-in on battery: see "USB light-sleep inhibit".)
11. *Found on the way: the clock after an RTC-domain reset.* Stage 1 of the RTC watchdog (and the super
    watchdog, a clock glitch) also reset the RTC timer, but `esp_reset_reason()` reports them as `ESP_RST_WDT`,
    which `timekeeping` treated as "the RTC kept counting": it would have claimed a synced clock at 1970. Now
    those reasons fall back to the NVS time anchor like a power-on.

**The safety net: an RTC watchdog that survives light sleep** (`components/health`). Armed first thing in
`app_main` (240 s while booting: a first boot formats LittleFS), then `CONFIG_PIXELCLIP_RTC_WDT_TIMEOUT_S` (default
40 s) once the controller loop runs. Stage 0 = system reset (the RTC clock keeps counting, so the time stays
right), stage 1 five seconds later = full RTC reset (backstop). Its *pause in sleep* bit is cleared, so it
counts on the RTC slow clock while the chip sleeps. The controller loop wakes at least every 5 s and feeds it,
**but only while every required liveness source has checked in** (player 30 s, power task 15 s, and since the
session hang of 2026-10-14 the httpd task, the lwIP thread and the NimBLE host too: see "Session hang
(2026-10-14)" below), so a stuck player, network stack or BLE host is a reboot too. Long controller steps (session start / stop) feed it as they progress. It is
stopped before deep sleep ("bye", battery floor); OTA restarts reconfigure it themselves. After such a reset
the splash replays, the clock comes from the RTC (stage 0) or the NVS anchor (stage 1), and the playlist
resumes. Limitation: it counts on the RTC slow clock, so a hang that also stopped the RC_FAST oscillator would
stop it too (not expected: IDF keeps RC_FAST on in sleep when it feeds the slow clock).

- Boot log: `app: PixelClip firmware booting (wake cause 0, reset reason RTCWDT_SYS (esp 7), boot #57)` (names:
  `POWERON`, `SW`, `PANIC`, `TASK_WDT`, `INT_WDT`, `BROWNOUT`, `DEEPSLEEP`, `RTCWDT_SYS` / `RTCWDT_RTC` /
  `RTCWDT_CPU`, `TG0WDT_SYS`, `SUPER_WDT`, ...). After a watchdog, brownout or panic reset a `W health:` line
  gives the counters; after **every** reset that kept RTC memory (also the RESET button on a wedged clip, which
  reports `POWERON`) two `W health: previous run ...` lines give the breadcrumbs: last beat per source, last
  feed, feeds skipped and which source was silent, the controller step (`session_stop:wifi`, ...), session or
  not, the internal heap at the last feed, uploads stored, the last HTTP request and whether its handler
  returned, the USB state, the USB hold (`usb hold on since 5 s`), the light sleeps with how many happened while
  `usb_present` was true (`56 light sleep(s) (0 while USB present)`; anything but 0 adds `: USB HOLD BROKEN`), and the
  last light-sleep entry / exit (`-> DIED IN LIGHT SLEEP`).
- Counters in NVS (namespace `health`): `/status` → `"resets":{"wdt":n,"brownout":n,"panic":n,"rtc_wdt":n,"last":"POWERON"}`
  (`wdt` counts every watchdog reset, `rtc_wdt` the RTC watchdog's share, `last` = this boot's reason).
- `E health: liveness: silent: player 31s: NOT feeding the RTC watchdog (reset within 40 s)` precedes a liveness
  reboot (the source names: player, power, httpd, tcpip, ble).

**Battery-mode policies** (no USB; `power_on_battery()`):

- A session started below **3.9 V** runs with the panel off (overrides `display_during_upload`; the "WiFi"
  card, then panel off, "Done" at the end, as a panel-off session). If the averaged reading drops below 3.9 V
  during a screen-on session, the panel goes off for the rest of it (`/status.session.display_on` turns false).
  Always-on sessions keep their screen (README "Always reachable").
- SoftAP TX cap **8 dBm on battery** (`CONFIG_PIXELCLIP_WIFI_MAX_TX_DBM_BATTERY`) vs 10 dBm on USB
  (`CONFIG_PIXELCLIP_WIFI_MAX_TX_DBM`); re-applied when USB comes or goes during a session.
- In a session, "low battery" (≤ `low_battery_pct`, < 3.40 V, or < 3.5 V) only **ends the session**; it never
  powers the clip off. After the session the 4-sample average restarts from rested readings, so the post-session
  low-battery decision is not taken on readings that sagged under TX. Each session logs its minimum:
  `power: session battery minimum: 3712 mV` (one ADC read per second during sessions).

**USB presence** (`battery.usb_present`, BLE status bit1; the app shows the bolt for `usb_present || charging`).
Re-evaluated every second in the power task (it used to follow the 30 s battery sample):

- `usb_present` = the USB-Serial-JTAG sees SOF packets from a host *now* — `usb_serial_jtag_is_connected()` is
  **not sticky** in IDF 5.5 (its FreeRTOS tick hook clears it 3 ms after the last SOF,
  `usb_serial_jtag_connection_monitor.c`) — **or** at least 3 of the last 5 one-second Vbat reads are ≥ 4.25 V (VBUS
  proxy for a wall charger, which sends no SOF: only the charger holds the BAT node that high).
- `charging` = `usb_present` and the averaged Vbat < 4.15 V.
- Unplugging clears it within ~1 s (computer) or ≤ 3 s (charger). The old rule took the 4.25 V threshold on
  a single sample (a cell fresh off the charger reads 4.18–4.20 V, plus the ADC's tolerance) and kept the flag
  for up to 30 s: the bolt seen on battery. Not used: "> 4.05 V with the cell at rest" — a full cell rests at
  4.15–4.20 V on battery for tens of minutes, so that clause would bring the false bolt back.

**Bench reproduction** (`CONFIG_PIXELCLIP_BENCH_SLEEP_TEST`, `main/bench.c`, `sdkconfig.bench`): automatic light
sleep also while USB is connected (no USB hold in this build, power.c; `CONFIG_USJ_NO_AUTO_LS_ON_CONNECTION=n`,
enforced with `#error`), an upload
session 20 s after boot for 40 s, every 120 s (`CONFIG_PIXELCLIP_BENCH_FIRST_S` / `_SESSION_S` / `_PERIOD_S`), a
4×4 px green heartbeat dot in the bottom-left corner toggled every second by a priority-1 task while the player is
alive (a frozen dot = player stuck, nothing changing = chip stuck), PM profiling, accounting errors fatal, and a
"console window" every 30 s at 45, 75, 105 … s (light sleep held off for up to ~4.5 s so the host re-enumerates
the port, then one line:
`bench: boot #N reset R up S s | sessions K (idle) | resets wdt .. rtc_wdt .. | light sleeps .. rejected .., P% of the time | heartbeat .. | perf .. | pm locks .. | battery ..`).

`sleep_soak.sh` counts boots (from the boot lines and the boot number in every status line), RTCWDT resets

## Crash diagnostics (core dump)

A panic (CPU exception, `abort()` / failed `assert`, interrupt watchdog, stack-overflow check) still prints
the usual panic report on the console and reboots, but first IDF writes an **ELF core dump** of every task
(registers, TCB, the live part of each stack; no `.bss`/`.data`/heap capture) to flash
(`CONFIG_ESP_COREDUMP_ENABLE_TO_FLASH`, ELF format, SHA-256 checksum; `sdkconfig.defaults`). The task
watchdog only logs (no panic) and an RTC watchdog / brownout reset is a hardware reset, so those leave no
dump: for them there are the RTC breadcrumbs below.

- **Partition:** `coredump, data, coredump, 0x12000, 0xE000` (56 KB) in the formerly unused gap between
  `phy_init` (ends 0x12000) and `ota_0` (0x20000, 64 KB aligned). Nothing else moved. The LittleFS `assets`
  partition was deliberately **not** shrunk: `esp_littlefs` here mounts with `block_count = 0`, i.e. takes
  the block count from the superblock, so a smaller partition would still mount with the old, larger
  count and later write past its end; shrinking it safely means reformatting = losing the stored
  content. The OTA slots keep their size too. 56 KB is enough for this app: per task the dump holds a
  340 B TCB, a 608 B register note and 64 B of program headers (~1 KB), plus the stack in use at the
  crash; with ~20 tasks that is ~21 KB fixed + typically 12–20 KB of stacks ≈ 35–45 KB (a deep crash
  in the 10 KB httpd stack included). Only if it ever did not fit would the panic output say
  `Not enough space to save core dump!` (IDF 5.5's ELF writer ignores `CONFIG_ESP_COREDUMP_MAX_TASKS_NUM`,
  so there is nothing to trim there; DRAM capture would need ≥ 128 KB and stays off).
- **Boot line** (every boot while a dump is stored, i.e. until it is deleted; flash.sh shows it as WARN):
  ```
  W (412) health: coredump: task player crashed at PC 0x4201a2b4, exccause 28 (LoadProhibited) vaddr 0x00000010, epc1 0x4201a2b4 ... backtrace 0x4201a2b4 0x42019f10 0x4200d7c2 (depth 3, corrupted no), reason "..."; 38912 bytes, app elf 3c1f6a2b0 (this firmware); GET /coredump to fetch, DELETE /coredump to clear
  ```
  `exc_task`, `exc_pc`, `ex_info.exc_cause` / `exc_vaddr` / `epcx`, `exc_bt_info` from
  `esp_core_dump_get_summary()`; `reason` is the abort / assert / watchdog text when there is one. The
  backtrace is a plain PC list: `idf.py monitor` decodes it, or
  `xtensa-esp32s3-elf-addr2line -pfiaC -e build/pixelclip.elf 0x4201a2b4 0x42019f10 ...`. "OTHER firmware"
  instead of "this firmware" means the dump is from an earlier build (OTA since): decode it with that
  build's `pixelclip.elf`. A partition with leftover data from an older layout or a dump with a bad checksum
  is reported once (`coredump: partition holds no valid core dump (...): clearing it`) and erased.
- **A core dump is an image of the clip's memory.** It holds what the tasks had on their stacks: names of
  assets and texts, pieces of requests, possibly text being shown. The firmware keeps the hotspot passphrase
  out of it (it lives in static memory, which is not captured, and is wiped from the one stack frame that
  hands it to the WiFi driver), but treat a dump like a private file all the same: do not attach
  `core.bin` / `firmware/e2e_coredump.bin` to a public bug report (both names are git-ignored).
- **HTTP** (WiFi; over the BLE fast lane `GET` is a WiFi-only route → 413 `use_wifi`):
  `GET /coredump` → 200 `application/octet-stream`, the raw flash image (header + ELF + SHA-256, with
  Content-Length), or 404 `{"ok":false,"error":"no_coredump",...}`. `DELETE /coredump` → 200
  `{"ok":true}` (erased) or 404 `no_coredump`. `GET /status` → `resets.coredump: true|false`.
- **Decode** (on the Mac, with the ELF of the firmware that crashed):
  ```
  curl -o core.bin $CLIP/coredump
  idf.py coredump-info -c core.bin                       # from firmware/, uses build/pixelclip.elf
  # or: python -m esp_coredump --chip esp32s3 info_corefile -t raw -c core.bin build/pixelclip.elf
  curl -X DELETE $CLIP/coredump
  ```
  Both print the crashed task's registers and call stack, every task's backtrace and the panic reason
  (`idf.py coredump-debug -c core.bin` opens GDB on it).
- **Old partition table:** a clip updated over OTA keeps the partition table it was flashed with, which has
  no `coredump` partition (only a USB `flash.sh` writes the new one; nothing else changes, so assets and NVS
  survive it). Such a clip boots without any core dump message or error (`components/health` wraps IDF's
  startup hook, which would otherwise log `No core dump partition found!` at every boot), `GET /coredump` and
  `DELETE /coredump` answer 404 `no_coredump`, `resets.coredump` is false, and a panic just reboots as before.

## Session hang (2026-10-14): liveness, awake holds, internal RAM, stress bench

**The incident (on USB, panel on).** 50.9 s: session up with `internal heap with WiFi up: 36263 B free, largest
block 25600 B`; 52.4 s the phone dropped BLE (reason 0x213, expected); 53.0 s the `water` scene (28.6 fps); 58.9 s
the phone joined; 62.0 s a 194 KB atlas was stored and the playlist reloaded; 62.5 s the USB serial port vanished
and never came back, and no reset followed for minutes. Earlier, on battery, the same signature followed a session.

**Why no watchdog reset** (code audit; the next boot's `health: previous run ...` lines will tell which case):
the RTC watchdog was fed by the controller whenever the *player* had beaten within 30 s. A clip whose player and
controller still run while WiFi / httpd / lwIP / BLE / USB are dead kept feeding forever (scene on screen, useless
otherwise). A full wedge of both cores would have reset it (the RWDT is hardware; nothing in IDF touches it at run
time: `sleep_modes.c` only arms its own 1 s guard when the RWDT is *not* already enabled, the panic handler feeds
it), and on USB the chip never light-sleeps, so "counts in light sleep" is not involved. The only path that stops
the RWDT is `power_off()` (deep sleep: "bye" after a 6 s hold, or the low-battery shutdown), which also kills USB:
if the panel was black, that is the candidate (low battery cannot trigger on USB with SOF; a 6 s BOOT glitch can).

**Liveness bitmap (now).** The controller (priority 1 = the lowest application priority, CPU0) feeds only when every
*required* source beat within its limit; the sources and probes are listed in `health.h`:
player 30 s and power task 15 s (always), httpd 30 s and lwIP 15 s (while a session is up: `httpd_queue_work` /
`tcpip_try_callback` probes every 5 s, plus beats on every recv / send of a running handler), NimBLE host 30 s
(while BLE runs and is synced: a ping event on its queue every 5 s). Long known operations call `health_grace()`.
Safety valve: three liveness resets in a row blamed only on httpd / tcpip / BLE relax those three for the rest of
that boot (logged), so a broken radio cannot reboot-loop the player. USB itself is not a liveness source (a host is
legitimately absent on battery); its state is a breadcrumb instead.

**Session light-sleep inhibit.** A session holds an `ESP_PM_NO_LIGHT_SLEEP` lock (`power_awake_acquire(SESSION)`)
from start until 10 s after it ends (`net: session: light sleep inhibited (until 10 s after the session ends)`, then
`net: session: light sleep allowed again`), and every BLE fast-lane worker holds one while it runs (released by the
worker before it frees the lane; until 2026-10-15 it was never released, see "Fast-lane hold leak" below). The esp_pm
light-sleep callbacks (`CONFIG_PM_LIGHT_SLEEP_CALLBACKS`) count entries made while any awake hold is held
(`light sleeps N, while inhibited M, while usb K` in every session heap line; `E net: ASSERTION: ...` if M > 0, fatal in the
bench builds) and record entry / exit in the RTC breadcrumbs. (The session's CPU_FREQ_MAX hold already prevented
light sleep; the explicit lock makes the rule independent of DFS settings and checkable.)

**Session-time safety.** While an upload body is received live scenes run at **15 fps** instead of 30 (`player:
scenes: upload in progress, 15 fps cap`; until 2026-10-15 it was 10 fps for the whole session): scene + WiFi + uploads
was the heaviest mix (CPU, PSRAM bandwidth, a 16 ms QSPI flush with its DMA interrupts every 33 ms). Refusing scenes was rejected: it would change what the app sees
(`playlist.current`) and break the e2e expectations. Heap is logged every 10 s during a session and after every
upload: `net: heap in session: internal N B free (min, largest), psram ... | uploads K | awake holds ... | liveness
player=0s power=0s httpd=2s tcpip=2s ble=1s` (`net: heap after upload <id>: ...`).

## Fast-lane hold leak and USB console loss (2026-10-15)

**Fast-lane hold leak.** The heap lines of a session read `awake holds session=1 fastlane=23` and after it
`esp_pm locks held: awake/NO_LIGHT_SLEEP x24`: one `ESP_PM_NO_LIGHT_SLEEP` hold per BLE fast-lane request since
boot (6 after the first sync, 23 after the second). Cause: the host task acquires `POWER_AWAKE_FASTLANE` when it
starts a worker (`pixelclip_ble.c` `fast_lane_frame`), and `api_worker` only released it on the "task creation failed"
path, never at its end. Effect: after the first fast-lane request the chip could never light-sleep again (on
battery: a drained cell instead of the ~1 mA BLE idle; it also hid every light-sleep path from the 2026-10-13
investigation). Fix: the worker releases its hold before it clears `s_busy` (also when a late error answer is
sent after the response, it re-takes the hold for it). Checks (log in production, `abort()` in the bench builds):
`pixelclip_ble_fast_lane_holds_ok()` reads a consistent snapshot (lane idle and no worker started before and after
reading the count; the host bumps a sequence number and sets `s_busy` before acquiring, the worker releases
before clearing `s_busy`, so an idle lane with a non-zero count is a leak) after every fast-lane request, in
every session heap line (`fastlane=N` must read 0 between requests), at session end and when the session's own
hold goes 10 s later (`net: session: light sleep allowed again (10 s after the session); awake holds session=0
fastlane=0`, `E net: ASSERTION: N session awake hold(s) left` otherwise):
`E ble: ASSERTION: N fast-lane awake hold(s) still held <when> with the lane idle (leak)`.

**USB console gone at 246 s.** Sequence: 234.5 s session end; 243.3 s a phone connected over BLE and dropped
at once (`LE Set Data Length` refused, reason 0x213); 244.5 s `light sleep allowed again`; ~246 s the host stopped
sending SOF (`USB no SOF since 246 s` in the next boot's breadcrumbs) and `serial_capture.py` lost the port;
every liveness source kept beating until 278 s (a second session even ran from 255 s, with HTTP requests at
264 s); at 279 s the port re-enumerated, the capture reopened it, and that open reset the chip
(`rst:0x15 (USB_UART_CHIP_RESET)`, see below). What the firmware did around 246 s, checked against the
USB-Serial-JTAG's needs (the USJ is a fixed-function device: enumeration, SOF and the CDC endpoints are hardware;
software can only break it by resetting the chip, powering down or clock-gating the USB PHY / its 48 MHz PLL
clock, or repurposing GPIO19/20):

- `light sleep allowed again` only decremented a lock that was still held 23 times (the leak above) plus the
  USJ driver's own `usb_serial_jtag` NO_LIGHT_SLEEP lock: no light sleep happened (breadcrumbs: `0 light
  sleep(s)`), so neither the PHY nor the PLL was touched.
- CPU frequency: the water scene holds the CPU_FREQ_MAX lock (160 MHz), and the DFS minimum is 80 MHz, which
  runs from the PLL: the USJ clock never stops with DFS here.
- WiFi: `esp_wifi_stop()` ran 11 s earlier (234.5 s) and identically after the first session (92 s), after
  which USB ran for 118 s. The PHY stays powered for BLE; `CONFIG_ESP_PHY_ENABLE_USB=y` keeps the PHY library
  from disabling the USB PHY when it initialises. Nothing calls the PHY or coexistence at 244–246 s.
- GPIO19/20 (USB D-/D+) are not used by the display, the IMU or anything else; nothing reconfigures them.
- The console has no USJ driver installed: the VFS writes to the FIFO directly and drops output after 50 ms
  without a host (`usb_serial_jtag_vfs.c`). That is the data path only; it cannot make the host stop SOF.
  **Installing the USJ driver was considered and not done**: it adds a TX/RX ISR and ring buffers but has no
  part in enumeration or SOF, so it would not make the link more robust; it would cost internal RAM the session
  needs.

Conclusion: nothing the firmware did at session end or at the 10 s release can disturb the USJ or its clock; the
SOF loss is most likely host-side (the Mac suspending / resetting the port, a hub, or the cable) and stays
unexplained from this log. For the next occurrence the power task now logs both SOF edges with their times
(`W power: USB host SOF lost at 246 s ...`, `W power: USB host SOF back at 279 s after 33 s without (lost at
246 s)`), and because the capture no longer resets the chip when it reopens the port, the console of the
running firmware (including those lines and anything it logged meanwhile that fit the FIFO) will be visible after
a re-enumeration instead of a fresh boot.

**The capture itself reset the clip.** Both the first open of that capture and the reopen at 279 s logged
`rst:0x15 (USB_UART_CHIP_RESET)`. The USJ holds the chip in reset while RTS is asserted with DTR clear (DTR at
the release selects download mode); the tools Espressif maintains for this peripheral are written against that
(esptool `USBJTAGSerialReset`, esp-idf-monitor `open_serial`: "set the RTS first to avoid reset"). macOS raises
DTR and RTS when a tty is opened, so the line state became (DTR 1, RTS 1); `serial_capture.py` had preset both
False and pyserial applies DTR before RTS inside `open()`: (0, 1) = reset, then (0, 0) = boot. Now the port is
opened as esp-idf-monitor does it: `serial.Serial()` unopened with `dtr=True`, `rts=True` preset (what the OS does
anyway) and `exclusive=True`, `open()` (no change on the lines), then `rts=False` → (1, 0), then `dtr=False` →
(0, 0); the sequence never passes through (0, 1), on the first open and on every reconnect. `--reset` remains the
only way the script resets the chip (an RTS pulse with DTR clear), and `NOFLASH=1 scripts/flash.sh` uses it on
purpose (it says so). Self-check: after every open the script watches 2 s for a ROM banner (`ESP-ROM:` /
`rst:0x`) and writes `[serial_capture: WARNING: port open caused a reset ...]` into the capture when one appears
without `--reset` (`--expect-boot` silences it right after esptool's own reset; `flash.sh` passes it after
flashing and reports the warning as WARN). Note: a capture started with the OLD script (still running) keeps
resetting on reconnect until it is restarted.

## USB light-sleep inhibit (2026-10-15)

**Evidence.** Two captures on USB: the next boot's breadcrumbs read `USB host (SOF) since 5 s; 56 light sleep(s)` — the
clip light-slept while plugged into the Mac — and each capture ended with `port lost` minutes after a session's
awake hold went (hold released at 327 s, port lost at 517 s, never re-enumerated). The user sees a crash.

**Why `CONFIG_USJ_NO_AUTO_LS_ON_CONNECTION` did not keep it awake** (IDF v5.5 sources). The inhibit does *not*
depend on the USJ driver: `usb_serial_jtag_connection_monitor.c` is linked through the USJ console, registers a
FreeRTOS tick hook at startup and takes its `usb_serial_jtag` NO_LIGHT_SLEEP lock whenever the hook sees the SOF
interrupt bit. So installing the driver would not have changed anything (that option is dropped). What does break it:

- The hook releases the lock after 3 ticks (`USJ_DISCONNECT_CONFIRM_PERIOD_MS` 3 = 3 ticks at 1 kHz) without the SOF bit.
  When the tick interrupt is held off for ≥ 4 ms, `SysTickIsrHandler` (`freertos/port_systick.c`) catches up by
  calling `xPortSysTickHandler()` — and so the hook — once per missed tick, back to back: the first call sees and
  clears the SOF bit, the next ones see none within microseconds, and the lock is released although the host never
  stopped. The next tick re-acquires it, but in between the idle task may enter light sleep. Our once-a-second
  `usb_present` sample does not see such a blip, which is why the breadcrumbs say "SOF since 5 s" next to 56 sleeps.
- Every light sleep on the S3 disables the USB-Serial-JTAG pad and its bus clock for the duration
  (`esp_hw_support/sleep_modes.c` `misc_modules_sleep_prepare` → `sleep_console_usj_pad_backup_and_disable`; the S3
  lacks `SOC_USB_SERIAL_JTAG_SUPPORT_LIGHT_SLEEP`): the host sees the device detach. Once the host has given up on
  the port, no SOF comes back, the IDF lock stays released, the chip light-sleeps for long stretches with the pad
  off, and the port never re-enumerates — the "port lost" at 517 s.

**The rule now** (`components/power`, `POWER_AWAKE_USB`, one more owner of the shared `awake` NO_LIGHT_SLEEP lock):

- Every second the power task evaluates `usb_present` = host SOF seen now **or** the VBUS proxy (3 of the last 5 Vbat
  reads ≥ 4.25 V; see "Light sleep on battery", USB presence).
- `usb_present` true → the USB hold is acquired *in that same tick, before `usb_present` is published* (also at boot:
  `power_init` evaluates USB and takes the hold before `esp_pm_configure` enables light sleep), log
  `I power: USB present: light sleep inhibited (usb hold, until 5 s after USB goes)`.
- `usb_present` false → the hold stays until `usb_present` has been false for 5 s (debounce: one missed SOF sample or
  a proxy flicker changes nothing), then `I power: USB gone for 5 s: light sleep allowed (usb hold released)`. With
  the 1 s tick that is 5–6 s after the last true sample.
- `CONFIG_USJ_NO_AUTO_LS_ON_CONNECTION=n` in `sdkconfig.defaults`: one rule, one owner. The SOF monitor itself stays
  (it is what `usb_serial_jtag_is_connected()` reads). No USJ driver is installed (unchanged).
- Not in the light-sleep soak build (`CONFIG_PIXELCLIP_BENCH_SLEEP_TEST`), which light-sleeps on USB on purpose.

**Checks.** The light-sleep callback counts entries made while `usb_present` was true (`light_sleeps_while_usb`, must
be 0; a USB-hold entry is also an ordinary awake-hold violation). Every power tick asserts that the hold matches
`usb_present` (held exactly when `usb_present`, or for at most 5 s + 2 s slack after it went false; never in the soak
build) and that no light sleep happened while `usb_present`: `E power: ASSERTION: ...` once per episode in production,
`abort()` in the bench builds (`BENCH=1`, `STRESS=1`). Visible in:

- the session heap lines: `awake holds session=1 fastlane=0 usb=1, light sleeps 0, while inhibited 0, while usb 0`;
- `app: after session: ... awake holds session=1 (until 10 s after) fastlane=0 usb=1 (light sleeps 0, while usb 0);
  esp_pm locks held: awake/NO_LIGHT_SLEEP x2, ...` and `net: session: light sleep allowed again (...); awake holds
  session=0 fastlane=0 usb=1` (on USB the `awake` lock stays held once: that is the USB hold);
- the next boot's breadcrumbs (`health: previous run: ... USB host (SOF) since 5 s; usb hold on since 5 s; 56 light
  sleep(s) (0 while USB present), ...`; crumbs v3, so the first boot after this update prints no previous-run lines);
- `GET /status` → `"power":{"usb_hold":true,"light_sleeps":0,"light_sleeps_while_usb":0,"awake_violations":0}`
  (extension; counters since boot). `scripts/e2e.sh` asserts the types and, when `battery.usb_present` is true,
  `usb_hold` true and `light_sleeps_while_usb == 0`.

**Cost:** none on battery. On USB the chip idles at the 80 MHz DFS minimum instead of light-sleeping (some tens of
mA more, not measured), which the USB supply covers. **Limitation:** plugging into a computer while the clip light-sleeps on battery is
detected by the SOF monitor only while the chip is awake (pad on), or by the VBUS proxy within ~3 s if the charger
lifts Vbat ≥ 4.25 V; a nearly full cell resting below that on a host that never gets to send SOF can delay the hold
(the BOOT button or any session wakes it; the first SOF seen then takes the hold).

## Robustness

- Every boot step after the event loop is non-fatal: a failure is logged as `BOOT STEP FAILED`
  and the clip continues (dead panel → headless but WiFi works; LittleFS formats itself if it cannot
  mount; NVS is erased on version/space errors; PM/ADC failures disable DFS/battery monitoring).
- Uploads are decoded frame by frame before they replace anything (corrupt RLE → 422). At boot,
  files with a bad header are dropped; unreadable ones are skipped, never deleted. A stored playlist
  item whose asset vanished is skipped, not the whole playlist. A frame that fails to read/decode
  during playback skips to the next item.
- **Safe start.** If the clip crashes (panic or any watchdog reset) three times in a row, each time within
  120 s of its boot, the fourth boot sets the stored playlist aside (`playlist.bad.json` on LittleFS, kept for
  a post-mortem over USB) and comes up idle: the hotspot and the BLE doorbell work, assets, texts and fonts
  are untouched, and the owner sends the playlist again from the app. This is the way out when stored content
  crashes the firmware at every boot (the nested-JSON playlist of the security audit did exactly that before
  the nesting cap). The streak lives in RTC memory (`components/health`, `health_safe_start()`); it is ended
  by every boot that is not a crash (power-on, RESET, a USB or flashing reset, the restart after an OTA, a
  deep-sleep wake, a brownout) and by any crash of a run that lived longer, so ordinary use never triggers
  it; a watchdog reset blamed only on the radio tasks (httpd, lwIP, BLE) does not count either. Log: `health: safe start: 3 boots in a row crashed within 120 s ...` and `app: safe start: stored
  playlist set aside ...`; while the streak builds, `health: N early crash(es) in a row (safe start at 3)`.
  Bench builds: three deliberate `/bench/crash` runs within 2 minutes of each boot trigger it too.
- Diagnostics: for 60 s after boot the log shows stack high-water marks of all tasks, heap
  (internal/PSRAM) and a one-line `summary:` every 10 s; each session end logs the httpd and
  controller stack high-water marks.

## Security hardening (2026-11 audit)

What the firmware does about the findings of the pre-release security audit that concern this folder. The
contract side is in `docs/PROTOCOL.md` §4 "Request checks", "Firmware update" and "Config JSON". What is
**not** done yet: the BLE link has no pairing, the hotspot passphrase is the published default until the owner
changes it (clients can now see that, `ap_password_set`), and firmware images are not signed (a press on the clip
is now needed before one is taken, but what it installs is whatever the sender sent).

- **Firmware update permission** (audit WIFI-2). `POST /ota` answers `403 press_button` unless someone pressed
  the clip's button while it showed "Update?" (60 s after `POST /ota/ask` or a refused `POST /ota`); the press
  allows updates for 120 s, until an image is accepted, or until the session ends. The decision is made from the
  headers, before any body byte is read. The state machine is `components/ota/ota_gate.c` (pure C, host-tested in
  `test_host/test_ota_gate.c`); `ota_permission_*()` in `ota.c` wraps it under a spinlock on the uptime clock for
  the httpd task (ask, check, clear after an accepted image) and the controller (press). `net_session_stop()`
  clears it. The prompt is an overlay of the controller (`app_main.c`, `overlay_sync()`): the player output is
  stopped and `system_screen()` draws it, waking the panel in a panel-off session; a timer at the window's edge
  puts the screen back as the mode has it (dark again in a panel-off session). The press that allows is used up
  (no next item, reader pause or oracle turn). Over the BLE fast lane `GET /ota` works and `POST /ota/ask` is
  WiFi only, so someone in Bluetooth range cannot put the prompt on the screen. Bench and stress builds send no
  `/ota` (`bench.c`, `sdkconfig.stress`, `sdkconfig.bench`, `sleep_soak.sh`), so they need no bypass and have none.
- **Hotspot password reset on the clip** (audit WIFI-5): five short presses within 3 s, then a long press within
  10 s (see "Using the clip"). The detector is `components/button/press_seq.c` (pure C, host-tested in
  `test_host/test_press_seq.c`); the reset is `appcfg_reset_ap_password()`, which overwrites the passphrase in
  place and rewrites `config.json` with everything else unchanged. Someone holding the clip could always erase it
  over USB; this gives the same physical-access recovery without losing the content.
- **`ap_password_set`** in the `GET /config` / `PUT /config` answers: whether the passphrase still is the factory
  default (computed when the answer is built, never written to `config.json`, ignored in a patch).

- **JSON nesting cap.** cJSON is built with `CJSON_NESTING_LIMIT=16` instead of ESP-IDF's 1000
  (`json_limit.cmake`, applied to the `json` component in `CMakeLists.txt`). Its parser recurses once per
  level (64 B of stack each, 96 B for the printer); a 2 KB body nested 1000 deep used to run 54 KB past the
  end of a 10 KB stack, and a playlist with an ignored key nested about 100 deep was stored and then crashed
  the clip at every boot. Deeper documents are now "not JSON": 400 `bad_json` on the routes, "stored playlist
  invalid, treating as empty" at boot. `net/http_api.c` refuses to compile if the definition did not arrive;
  `test_host/test_json_depth.c` builds ESP-IDF's own `cJSON.c` with the same number and checks the boundary.
- **The passphrase is write-only.** `GET /config` and the `PUT /config` answer never contain `ap_password`;
  over the fast lane a `PUT /config` carrying it is refused. In memory it is kept out of `appcfg_t` (copies of
  which sit on task stacks, and task stacks are what a core dump captures): `appcfg_get_ap_password()` is the
  only reader, `net.c` wipes its copy once the driver has it.
- **Request checks** (`http_request_allowed`, `json_type_ok` in `net/http_api.c`; HTTP only): no request with
  an `Origin` header, a foreign `Sec-Fetch-Site` or a `Host` other than the clip's address / `pixelclip.local`
  is served, and JSON bodies must be `application/json`. Together these keep a web page in the phone's
  browser from driving the clip while the phone is on the hotspot (a page can only send form or `text/plain`
  bodies cross-origin without a preflight, always with `Origin`), and close DNS rebinding.
- **Slow clients** (`net/http_api.c`, "slow-client guard"). The server runs every connection on one task, and
  the controller waits for that task when a session ends, so a client that stalled used to end in an RTC
  watchdog reset. Now: socket timeouts of 5 s (every wait ends, beats the liveness source and notices a
  session end at least that often); request line + headers within 10 s and without a 5 s pause (`408`); a body may be silent for 30 s and a
  response for 10 s (the totals the old 3 × 10 s and 1 × 10 s gave); and whenever the server has spent 30 s
  blocked on a client, at least 4 KB must have moved (137 B/s; only time spent waiting for the client
  counts, never flash writes or hashing). For scale: the app allows a whole transfer 5 minutes and gives up
  after 20 s (assets) to 60 s (firmware) without progress, and a 5 MB upload over a poor link still moves
  tens of KB per second. An upload cut by these rules, or by the session ending (long press, BLE `0x02`,
  weak battery, power off), is abandoned cleanly within 5 s: temp file removed, OTA aborted, no reset.
  The session's idle timer is refreshed while bytes move, so a long transfer cannot time the session out.
- **`low_battery_pct` 0–20**, and the **WiFi-only development routes** (`/imu`, `/imu/calibrate`,
  `/queue/test`): see "Protocol interpretations" 10 and 19.
- **SoftAP ciphers.** The audit read the configuration as "TKIP still offered, PMF off". On ESP-IDF v5.5.0
  that is not what goes on air: for `WIFI_AUTH_WPA2_PSK` the WiFi library (`wifi_softap_set_config` in
  `libnet80211.a`) overwrites the pairwise cipher with CCMP and sets PMF capable (not required), whatever the
  two fields say (`esp_wifi_types_generic.h` documents the same for `authmode`). So `net.c` is unchanged
  there. Not checked on air.
- **Safe start** after three early crashes in a row: see "Robustness".

### Hardening options

`sdkconfig.defaults` enables two compiler / RTOS options (neither touches eFuses or the bootloader); image
sizes measured on this tree with ESP-IDF v5.5.0:

| Build | `pixelclip.bin` | Static internal RAM (DIRAM) |
|---|---|---|
| before the audit fixes | 0x14c070 (1 359 984 B), 57 % free | 164 611 B |
| the fixes, no option | 0x14d340 (+4.8 KB) | +216 B |
| + `CONFIG_COMPILER_STACK_CHECK_MODE_NORM` | +11.5 KB (0.8 %) | +668 B |
| + `CONFIG_FREERTOS_WATCHPOINT_END_OF_STACK` | +0.2 KB | +48 B |
| both (the default build) | **0x150050 (1 376 336 B), 56 % free** | 165 543 B |
| (not enabled) `CONFIG_HEAP_POISONING_LIGHT` | +0.9 KB | +536 B, plus 8 B per live allocation |

- **Stack protector (normal).** A canary in the functions that have a local array of 8 bytes or more,
  checked on return: an overrun of such a buffer is a clean panic instead of a hijacked return address. Two
  instructions on entry and exit of those functions; the per-pixel loops of the renderers are not affected
  (the check is per call, not per iteration).
- **Stack-end watchpoint.** A hardware watchpoint on the last 32 bytes of the running task's stack: a stack
  overflow panics at the first write, where the FreeRTOS canary only notices at the next context switch,
  after the heap block below the stack has been overwritten. Costs one debug register (gdb has one hardware
  watchpoint less) and a few instructions per context switch.
- **Light heap poisoning is off on purpose.** It costs 8 bytes of *internal* RAM for every live allocation
  (several hundred of them: FreeRTOS objects, driver state, lwIP and NimBLE control blocks), in a firmware
  whose sessions run with about 36 KB of internal RAM free, and it could not be measured without a clip.
  To try it: add `CONFIG_HEAP_POISONING_LIGHT=y`, flash, and compare the `net: internal heap with WiFi up`
  and `heap in session` lines with and without it; enable it for good if the difference is a few KB at most.
- Not enabled, and not recommended as defaults: Secure Boot, flash encryption, NVS encryption, anti-rollback
  and the JTAG / download-mode eFuses. They burn eFuses for good and turn a mistake into a dead board. Anyone
  with the clip and a USB cable can therefore read and rewrite everything on it, including `config.json`
  with the passphrase in clear.

### ESP-IDF version

Built and tested with **ESP-IDF v5.5.0** (`dependencies.lock`). Two audit findings are fixed upstream rather
than here, so build release images with **ESP-IDF 5.5.5 or later in the 5.5 series** once it has been
through a regression run on a clip (`scripts/flash.sh`, `scripts/e2e.sh`):

- v5.5.0's SoftAP DHCP server reads past the end of a crafted option list from a joined station
  (`lwip/apps/dhcpserver/dhcpserver.c`; CVE-2026-45160, reported fixed in 5.5.5). Worst case a crash.
- 5.5.1 to 5.5.3 fix controller asserts on the ESP32-S3 and a NimBLE array overflow on an invalid connection
  handle; and before BLE pairing is switched on, the NimBLE fix for a NULL dereference in the SMP LTK request
  (CVE-2026-45816) must be in the release used.

`main/idf_component.yml` still says `>=5.5.0`: the version on this machine is shared with other projects and
was left alone. After moving, regenerate `dependencies.lock` and consider pinning `>=5.5.5,<5.6` there.

### Scripts

`scripts/e2e.sh` treats everything the clip returns as data: nothing from a response reaches Python `eval`,
shell arithmetic or a command, values it keeps are read with typed readers (integer / boolean / one of a
list) and device text is printed as printable ASCII only. It joins `PixelClip-XXXX` with the published
passphrase, so the "clip" it talks to may be anyone's. `scripts/ble_api.py` and `scripts/ble_wake.py`
connect to the strongest `PixelClip-*` they hear unless a name is given: with someone else's clip in range,
pass the name (`--name PixelClip-XXXX` / the first argument).

## Known limitations

- **Hardware status.** Running on the board: display (full flush 16 ms at 40 MHz QSPI), button, hotspot
  and the full HTTP API from the iOS app; boot 3.8 s; IMU found at 0x6B. Not yet seen on the board (this
  pass is build-only): the screen-on session flow and connection dot, always-on, the BLE doorbell
  (advertising, `scripts/ble_wake.py`, coexistence during a session), the BLE fast lane (`scripts/ble_api.py`,
  MTU / timings / flow control; only the framer is unit-tested, `test_host/`), BLE light-sleep current, and the
  internal-heap margin with BLE + WiFi up. Current draw in general is unmeasured. Also build-only so far: the
  "Update?" prompt and the password reset gesture (how the screens look, the press timing by hand, the panel
  waking in a panel-off session; the state machines themselves are host-tested and the mock runs the HTTP side).
- IMU axis mapping is an assumption until the bench check above; scene performance (fps) is only
  estimated until the `scene:` log lines are seen on the board.
- Queue entries never fire during a panel-off upload session; windows and the queue need
  `time.synced` (a sync from the phone within 24 h since power-on/deep-sleep wake), so after a
  "bye" power-off and wake the queue waits for the next sync (an approximate clock never fires them).
- QSPI runs at 40 MHz (what the Waveshare demo uses). Expected full-frame flush ≈ 14–16 ms; 80 MHz
  is selectable in menuconfig but untested on this panel.
- No tearing-effect sync (TE is on GPIO9, shared with the SD net); fast animations may tear.
- Frames are streamed from LittleFS per frame. RLE dark frames (1–5 KB) are fast; raw or busy
  full-screen frames (~257 KB) read at LittleFS speed and will cap the frame rate well below 30 fps.
- `clock` and `text` playlist items are accepted (valid types) but skipped by the player.
- Strip scrolling speed/fps is estimated (compose + full flush per frame) until the `strip:` log lines
  are seen on the board; a strip needs its decoded size + 512 KB as one free PSRAM block (see Scrolling
  strips; the boot diagnostics now log the largest free PSRAM block: `psram N free (largest M)`).
- `charging` / `usb_present` are heuristics (the PL4054 has no status line to the MCU), re-evaluated every
  second: `usb_present` = a USB host sends SOF packets right now, or 3 of the last 5 one-second Vbat reads
  ≥ 4.25 V; `charging` = `usb_present` and the averaged Vbat < 4.15 V (rule and reasoning in "Light sleep on
  battery"). A plain wall charger with a full cell reads as not present.
- Time trust: `time.synced` is false after power-on or deep-sleep wake, or 24 h after the last
  `POST /time`. After a reboot the clock is rebuilt from the NVS time anchor (see "Clock and time
  anchor"): approximate, assuming the clip was off for ~0 s after a power loss, so the clock is late by
  however long it was really off. The app should re-sync on every connection.
- Max 256 assets, 8192 frames per asset, strips ≤ 8192 px wide, 128 playlist items, 64 queue entries,
  128 remembered done queue ids, 64 texts (≤ 1 MB each), 32 reader fonts, 64 remembered reading positions.
- Reader timing on the board (paint + flush per word, light sleep between words) is estimated until the
  `reader:` log lines are seen; the e2e does not check the word pacing.
- The connection dot can overlap the reader's pause mark (both top-right); the dot is drawn on top.
- While an upload replaces or deletes the animation / text on screen, that item freezes for the
  duration of the store's validation + rename (typically well under a second) and then restarts.
- BLE: no pairing, so anyone in range can open the hotspot (as with the button); a 2.4 GHz-heavy
  session (big uploads) shares airtime with advertising. Not measured: advertising current, range at
  0 dBm through hair.

## Protocol interpretations (for the app)

These are places where `docs/PROTOCOL.md` left room; the firmware does exactly this:

1. **409 on PUT /assets**: returned only when the *same id* already holds a file with the same
   SHA-256 and size, checked from the headers before the body is read. Body:
   `{"ok":false,"error":"exists","message":...,"id","size","sha256","width","height","frames","atlas"}`.
   Same content under a different id is stored again. Different content under an existing id
   replaces it (201).
2. **PUT /assets errors**: missing/invalid `X-Content-SHA256` → 400 `missing_sha256`; bad id →
   400 `invalid_id`; empty body → 411; hash mismatch → **422 `sha256_mismatch`**; invalid `.hca`
   header/frame table, any frame that does not decode exactly, `data_size` ≠ body length, a
   non-atlas non-strip asset not exactly 536×240, or a strip (`is_strip`) that is not 1 frame of
   537–8192 × 240 (or is also an atlas) → 422 `malformed`; no space or more than 256 assets → 413
   (`no_space` / `too_many_assets`).
3. **`"ok":true` on document GETs**: `GET /config` and `GET /playlist` return the
   document with an extra `"ok":true` key (the general rule that success responses carry it).
   Ignore it when decoding.
4. **PUT /playlist**: playlist items referencing an unknown id *or a glyph atlas* → 422
   `unknown_asset`; bad shape → 400 `bad_json`; bad values → 422 `invalid_playlist`. Missing
   `transition` = config `default_transition`; missing `loops` = 1; `version` must be 1 if present.
5. **POST /show/{id}**: without `duration_ms` (or 0) the item plays **60 s**, then the playlist
   resumes at the item that was interrupted. The body may also carry `"scroll"` (see 36). Unknown id → 404 `unknown_asset`.
   `/next` or `/prev` during a "show" returns to the playlist.
6. **The display stays on during the session** (PROTOCOL §3 says the clip "blanks the display";
   config `display_during_upload`, default true, overrides that): after a 2 s "WiFi: PixelClip-XXXX" splash
   (PROTOCOL: 3 s) the content keeps playing with a 6×6 connection dot top-right (steady = waiting,
   pulsing = a client is associated). `/show`, `/next`, `/prev`, `/brightness`, `/reader`, `PUT /playlist`
   take effect live ("show" timers start at once), queue entries and windows fire as usual, and
   `GET /screenshot` returns the live framebuffer (without the dot). When the session ends the content
   continues (the "Done" card only follows a long press). With `display_during_upload: false` the old
   behaviour applies: 3 s splash, panel off for the whole session, `/show` & co. take visible effect when
   it ends, `GET /screenshot` = the frame that will be shown on resume (re-rendered offscreen), "Done"
   card at the end.
7. **`/brightness`** is not persisted; `PUT /config {"brightness"}` persists and applies.
8. **`tz_offset_s`** is stored once (NVS) and shared: `POST /time` and `PUT /config` both set it;
   `POST /time` without `tz_offset_s` keeps the current offset. `epoch` must be in 2020..2100.
9. **`/status`** adds `battery.usb_present` (bool). `playlist.current` is the asset id (other kinds:
    `scene:<id>`, `reader:<id>`, `oracle:<id>`, `board:<id>`), or `null` on the idle screen; `index` is -1 for an empty playlist. `device.id` / SSID use the
    last two bytes of the **SoftAP** MAC.
10. **Config validation** (422 `invalid_config`): `name` 1–64 bytes UTF-8, `brightness` 0–255,
    `upload_timeout_s` 30–1800, `ap_password` 8–63 printable ASCII (takes effect next session; **write-only**:
    no `/config` answer contains it, and over the BLE fast lane the key is refused with 413 `use_wifi`; the
    answers carry the read-only `ap_password_set` instead, false while it is the factory default),
    `low_battery_pct` 0–20 (was 0–50: at 50 one request switched the clip off below half charge; a stored
    higher value is clamped to 20 at boot), `default_transition` cut|fade, `tz_offset_s` ±50400, and the booleans
    (JSON `true`/`false` only; numbers, strings, `null` → 422) `display_during_upload` (default true,
    next session), `wifi_always_on` (default false, applies to the running session at once),
    `ble_wake` (default true, starts/stops BLE at once). All three are persisted in `/config.json` and
    returned by `GET`/`PUT /config`.
11. **Errors**: unknown path → 404 `not_found`, wrong method → 405 `method_not_allowed`, both in
    the JSON error format.
12. **Extension** (to be added to PROTOCOL.md): `GET /batlog` (text/csv), `DELETE /batlog`.
13. **Windows**: PROTOCOL says "Item-level `from`/`until` are local times of day (`HH:MM`, using the
    device's `tz_offset_s`)" and "Omitted = always active". With only one of them given, the other
    defaults to 00:00 / 24:00. `"24:00"` is valid for `until` only; `from == until` (empty window) and
    anything not exactly `HH:MM` → 422 `invalid_playlist`. Windowed items count as **inactive while the
    clock is not synced** (same rule as the queue's "queue entries do not fire while `time.synced` is
    false"), so an unsynced clip shows only unwindowed items (or idle).
14. **Queue entries**: `id` is 1–40 printable ASCII characters (0x20–0x7E, spaces and quotes included; PROTOCOL says "printable characters"; non-ASCII → 422), unique in the
    document; `at` is unix seconds in 2020..2100; `type` asset|scene|reader|oracle|board (clock/text → 422); the asset
    id is under `"asset"` (as in the PROTOCOL example) and must exist (422 `unknown_asset`);
    `duration_ms` 0 or missing = 60 s; `transition` missing = **fade** ("the device fades to that
    content"). At most 64 entries. Stored entries whose asset vanished stay in the queue and are
    marked skipped when due. `DELETE /assets/{id}` also removes queue entries that show it.
15. **"fire once ... remembered as done across reboots (keyed by `id`)"**: done = fired or skipped;
    persisted at the moment it fires. `PUT /playlist` forgets only ids absent from the new document.
16. **"A queue entry wins over a running `/show`"**: it replaces the show (which is dropped); a show
    sent during a queue entry is played after it.
17. **`/status`**: `queue.next_at` is `null` when nothing is pending; extra key `queue.active`.
    For a scene, `playlist.current` is `"scene:<id>"` (cannot collide with an asset id).
18. **Scene items**: `duration_ms: 0` = 60 s. `params` values must be strings (enum params) or integers
    / booleans (int params; booleans map to 1/0, a numeric string is accepted too); errors are 422
    `unknown_scene` / `invalid_params`. `seed` must be an integer 0–4294967295 (else 422
    `invalid_playlist`); on non-scene items it is ignored.
19. **Extensions** (non-normative, for development/bench): `POST /queue/test {"id"}`, `GET /imu`,
    `POST /imu/calibrate {"step":"upright"|"faceup"|"reset"}`. WiFi only (413 `use_wifi` over the fast lane).
20. **Strips**: "`GET /assets` reports `"strip":true` and the width": every asset carries `"strip"`
    (false for non-strips), the width is the existing `width`. "width up to 8192, height 240" plus the
    task's lower bound: 537–8192 (a 536-px strip is just a still and is rejected).
21. **`scroll`**: "`px_per_s` (10–400)" accepts fractions; `gap_px` and `loops` must be integers;
    missing keys default to 80 px/s, `left`, 0, 1 (the PROTOCOL gives no defaults; the app always sends
    all four). "`loops` passes": a pass ends when the copy has fully left the screen, so the item lasts
    `536 + loops·width + (loops−1)·gap_px` px of travel (matches PixelClipKit's `StripScroller`). `scroll` on a
    non-strip asset (or another item type) is validated but ignored.
22. **Scrolling queue entries**: "fades to that content for `duration_ms` (default 60 s)" is applied
    to strips too: without `duration_ms` a scrolling queue entry scrolls for 60 s (copies repeating)
    rather than `loops` passes (as the app's PlaybackEngine does).
23. **Fire `smooth`**: the firmware default is 1 while `GET /scenes` (registry verbatim) reports 0; an
    explicit `smooth` in the item always wins.
24. **Reader timing** — PROTOCOL: "60000/wpm ms × a factor: ×1.3 for words ≥ 8 chars, ×1.6 for ≥ 12, +50 % after
    a comma/semicolon, +100 % at sentence end, and a 300 ms blank at paragraph breaks". The bonuses add to
    the factor: factor = 1.0 / 1.3 / 1.6 + 0.5 (comma, semicolon, or a word ending in an en/em dash) or + 1.0
    (sentence end, wins over the comma), rounded to whole ms. "chars" = the word's core: glyphs from its
    first to its last letter/digit, so quotes, brackets and the trailing punctuation do not count (a word
    with no letter counts all its glyphs). A sentence end is `. ! ? …` (and full-width forms) as the last
    glyph that is not a closing quote/bracket or no-break space (abbreviations like "M." also pause). A
    paragraph break is a blank line (≥ 2 line breaks with only whitespace between, CRLF counts once) or
    U+2029, plus the end of the title line; the 300 ms blank follows the word, after its own time.
25. **"The first line of the file is the title"**: it is reported in `GET /texts` (trimmed, ≤ 63 bytes) and is
    also read as the first words, followed by the paragraph blank.
26. **Word segmentation** (`core/include/rsvp.h` header comment): whitespace separates (no-break spaces U+00A0 /
    U+202F join, so "«&nbsp;Bonjour&nbsp;!&nbsp;»" is one word); U+2019 and hyphens stay inside words; an en/em
    dash ends the word it is attached to ("oui—non" → "oui—", "non"); words longer than 32 glyphs are split.
27. **ORP** — "the Spritz rule (length 1 → 0, 2–5 → 1, 6–9 → 2, 10–13 → 3, else 4)": length is the core length
    in glyphs (not bytes), the index is counted from the first letter ("«Bonjour" → the 'n'). The ORP
    glyph's advance is centred on x = 230 (±0.5 px); a word too wide for the normal size uses the compact
    size; if even that overflows with the ORP pinned it is shifted to fit (or clipped when wider than the
    screen).
28. **Font document**: the glyph's pen origin is the cell's left edge, `baseline` is the baseline's row in the
    cell; black atlas pixels are transparent (cells may overlap their neighbours). Both sizes share one
    screen baseline. Glyphs missing from the font use the `?` glyph (nothing is drawn if `?` is missing
    too); spaces/no-break spaces use the advance of `" "` or `cell_w/4`. `PUT /fonts` → 201; 422
    `malformed` (document, or an atlas with another cell size / too few frames), 422 `unknown_asset` (atlas
    not uploaded or not an atlas), 400 `invalid_id`, 413 `too_large` (> 16 KB) / `too_many_fonts`.
29. **`PUT /texts`** (same style as assets): 201 `{"ok":true,"id","bytes","words","title","progress_word",
    "sha256","minutes"}`; 409 `exists` for the same id + hash + size; 400 `invalid_id` / `missing_sha256`;
    411 empty; 413 `too_large` (> 1 MB, from Content-Length), `no_space`, `too_many_texts`; 422
    `sha256_mismatch`, 422 `malformed` (invalid UTF-8, a NUL byte, or no word at all).
30. **Reader items**: `text` and `font` must be stored (else 422 `unknown_text` / `unknown_font`); `wpm` an
    integer 50–1500 (default 300), `from_word` an integer ≥ 0, `loop` a boolean (else 422 `invalid_playlist`).
    "`from_word` overrides it": a value > 0 sets the text's progress when the playlist is PUT; 0 or absent
    resumes the saved progress (0 when none). A position beyond the end starts at 0.
31. **Controls**: "short press pauses/resumes (instead of next); a double press skips to the next playlist
    item" — double = two short presses whose releases are ≤ 400 ms apart. `POST /reader` without a reader
    item on screen → 409 `no_reader`; unknown action → 422 `invalid_action`; seek without an integer word or
    beyond the last word → 422 `invalid_word`; missing action → 400. `GET /reader` without a reader item →
    200 with `"active":false,"text":null`. Extensions: `GET /texts/{id}`, `GET /fonts`, `DELETE /fonts/{id}`,
    `active` / `font` / `title` / `end_card` in `GET /reader`, `sha256` / `minutes` in `GET /texts`.
32. **`/status.session`** (extension): besides `idle_s` / `timeout_s`, `always_on` (bool: no idle timeout,
    `/session/end` ignored), `display_on` (bool: this session is screen-on; fixed when it started) and
    `clients` (stations associated to the SoftAP).
33. **`POST /session/end` with `wifi_always_on`** → 200 `{"ok":true,"always_on":true,"message":...}` and the
    hotspot stays up. PROTOCOL §3 says the AP shuts down "immediately on POST /session/end": always-on is an
    explicit opt-out of that. A long press, BLE `wake` 0x02 or `PUT /config {"wifi_always_on":false}`
    (the session then gets its idle timeout back) end it.
34. **`GET /ble`** (extension) → `{"ok":true,"enabled":bool,"name":"PixelClip-XXXX","service_uuid":"737B9B00-A500-43FC-B410-86AC8852E678","connected":bool}`.
    The BLE contract itself is `components/ble/include/pixelclip_ble_uuids.h` (see "BLE doorbell").
35. **Replacing / deleting what is on screen** during a screen-on session (`PUT`/`DELETE /assets/{id}`,
    `/texts/{id}`) works as before: the item freezes for the duration of the store, then restarts with the
    new content (or the rotation moves on after a delete). The responses are unchanged.
36. **`POST /show/{id}` `scroll`** (extension; PROTOCOL §4 says only "a strip uploaded without `scroll` plays as a
    still"): `{"duration_ms":…, "scroll":{"px_per_s","direction","gap_px","loops"}}`, validated like a playlist
    item's (bad → 422 `invalid_scroll`), ignored for non-strips. A strip shown without one borrows the scroll of
    the first playlist item, then queue entry, showing that asset (minus `loops`), else 80 px/s left gap 0: a
    shown strip always scrolls. Duration: `duration_ms`, else the request's own `loops` passes, else 60 s.
37. **Clock states** (extension of `/status.time`): `"approximate":bool` and `"anchor_age_s":int|null` (see
    "Clock and time anchor"). Approximate time never fires queue entries or opens windows (the PROTOCOL rule is
    "do not fire while `time.synced` is false"). `POST /time` clears `approximate`.
38. **Lone item** (PROTOCOL §4 "duration_ms > 0 wins"): when the rotation has exactly one active item,
    `duration_ms` is ignored and it plays indefinitely (stills held, animations loop seamlessly, strips scroll
    endlessly ignoring `loops`, scenes run on); a reader item honours its cap and holds its end card
    instead of restarting. See "Lone item".
39. **BLE fast lane** (PROTOCOL §3b). "`STATUS SP LF [body]`": the three-digit code, one space, LF (no reason
    phrase), e.g. `200 \n{...}`. "bits 0–5 = sequence (mod 64)": senders start at 0; the clip accepts any
    starting value and checks +1 per frame; a gap is answered `400 \nbad_frame` (plain-text body, not JSON)
    once, then frames are dropped until the next first frame; a new first frame while a request is open
    silently replaces it. "Max 16 KB per request": 16 384 bytes of body, plus the request line (so every
    document the HTTP endpoints accept fits); responses are capped at 16 384 bytes of body too (larger →
    413 `use_wifi`). "one request in flight": until the last frame of the previous response has been
    queued; a second request is consumed and answered 429 `busy` after the running response. "the device
    answers `413` for them": `413 \n{"ok":false,"error":"use_wifi","message":...}` (the usual error shape).
    `GET /texts/{id}` (not in the §3b list, an extension) is allowed and works up to the 16 KB response cap.
    "does not touch the session idle timer": also not through `PUT /config {"upload_timeout_s"}` (the new
    timeout counts from the last HTTP request). `req` also accepts writes with response.
40. **`/status.resets`** (extension): `{"wdt","brownout","panic","rtc_wdt","last"}`: reset counters kept in NVS since
    it was created (`wdt` = every watchdog reset, `rtc_wdt` = those by the RTC watchdog, i.e. the light-sleep
    safety net), `last` = the reason of this boot (`POWERON`, `SW`, `PANIC`, `RTCWDT_SYS`, ...). Also over the fast
    lane. `/status.session.display_on` can turn false during a session (battery below 3.9 V on battery).
41. **`/status.power`** (extension, 2026-10-15): `{"usb_hold":bool,"light_sleeps":int,"light_sleeps_while_usb":int,
    "awake_violations":int}`: power.c's USB light-sleep hold and the automatic light sleeps since boot, of which while
    `battery.usb_present` was true and while any awake hold was held (both must stay 0). See "USB light-sleep inhibit".
42. **Oracle sentence reader** (PROTOCOL §5f.1, 2026-10-18): the paragraph's state is reported as `"reading-out"` in
    `/status.oracle.state`; `/status.oracle.reading` is always present (`""` outside that state). Since §5f.3 the
    paragraph is shown as pages (no typing) and `page` counts them.
43. **Oracle paging** (§5f.3, 2026-10-18): `POST /oracle/back` (extension) is the double tap: the previous screen,
    answered like `/oracle/turn`; in `waits` and during a shuffle it changes nothing (200). `hold_ms` counts from the
    last tap / back / draw / shake (auto-advances by `face_ms` / `page_ms` do not reset it).
44. **One reading** (§5f.4, §5f.6, 2026-10-19): the short screens report `state` `"short"` with `page` = the screen
    (0–2; a screen's second page keeps its number); a bad forced row in `POST /oracle/draw` is 422 `invalid_cards`;
    the next random draw never repeats the previous three as a set (a 3-card deck has only one).
45. **The lean draw** (§5f.7, 2026-10-19): `state` `"lean"` with `page` 0–4 and `"detail"` with `page` 0–2 (A, B, C)
    and `card` the detail card; `reading` = that screen's text, the paragraph in `three` / `hold`. A lean screen with
    no text ("together" without a finding) and a card without `card.<i>.brief` are skipped both ways. The detail
    screen is the brief at full width without the card picture. "Fits one page" for the "and" screen is the
    firmware's page test with the body font; the reference rule (≤ 150 code points, `ORR_LEAN_PAGE_CHARS`) is what
    the app mirrors. The two agree whenever 150 characters fit one full-width page at the body size
    (with the bundles in `core/fixtures/tarot/` no lean screen is longer); a smaller page would make the clip pick the finding or the
    closing alone where the app shows both. A `notes` asset in an item is ignored.
46. **Arming and no interruptions** (§5f.8, 2026-10-19): `state` `"armed"` (cards_drawn −1s, `card` / `page` −1,
    `reading` `""`). `POST /oracle/draw` deals from any screen (the app's draw is not gated; only shakes are). "A draw
    in progress" is every state but `waits` (`armed` included), whatever started the oracle (rotation, `/show`, queue
    entry): its own end waits too. `POST /queue/test` acts at once like `/show`. The shake metric
    is polled only on `armed` (the core uses up a shake's edge on any screen it sees it, but on `waits` nothing wakes
    the oracle to look, so a shake already going on when the deck is armed deals at the first poll, ≤ 50 ms later).
47. **Cards, keywords and text as big as fits** (§5f.10 – §5f.12, 2026-10-20): `keys` is optional; when given it is
    checked and its delete drops the item, as the deck's. The keyword row is not shown during the shuffle (the
    shuffle's slots carry random cards). The "and" lean screen's page test stays "one page in the normal face" (in
    the 520 × 224 full-width box, core `ot_lean_fits`); the screen itself may then be drawn in the large face. A text
    that fits no face is drawn in the compact face, cut at its page (logged as `cut`). Whether a detail shows its card
    is decided once at the item's start (the box beside the card has the same size in both orientations). A font
    whose large atlases fail to load runs with normal / compact (logged), it does not stop the item.
